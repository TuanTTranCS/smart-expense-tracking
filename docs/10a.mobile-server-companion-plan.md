### Endpoint configuration

- Fixed scheme/host: `http://127.0.0.1`. Persist port `8080` and API base path `/v1` by default; show `http://127.0.0.1:8080/v1` as the active endpoint.
- Accept explicit decimal ports 1–65535. Normalize one trailing slash away. A base path starts with `/` and consists of nonempty ASCII segments containing letters, digits, `-`, `_`, or `.`; reject `.`/`..` segments, repeated slashes, backslashes, percent escapes, whitespace, query/fragment delimiters, and an empty/root-only path. Example custom endpoint: `http://127.0.0.1:8091/expense/v1`.
- Routes concatenate the normalized base path and `/models` or `/chat/completions`; avoid URI resolution that replaces the configured prefix. Neither app accepts redirects for the integration.
- Persisted settings and active settings are separate snapshots. Port/path/key changes while serving require explicit Stop, then Start; do not advertise unapplied draft settings as active. Failed bind leaves running false and shows the actual failure.

### Discovery and inference

- `GET <base>/models` returns `{"object":"list","data":[{"id":"<exact model ID>","object":"model","owned_by":"local"}]}`. List initialized usable LiteRT-LM models; return an empty array when none are ready. Discovery is not a vision-quality or inference-success check.
- `POST <base>/chat/completions` accepts `model`, `messages`, and `stream` absent or false. The expense app currently omits `stream`; preserve non-streaming as the default.
- The supported extraction subset is zero or more text-only system messages followed by one user message. Its content is a string for typed expenses or an array of `text` and `image_url` parts for one receipt photo. Reject assistant/history replay, unknown roles/parts, audio, tools, empty input, and streaming requests with explicit 400 errors. Full OpenAI API compatibility is outside this fork's integration contract.
- Image requests contain exactly one inline `data:image/jpeg;base64,...` or `data:image/png;base64,...` image and at least one nonblank text part. Concatenate text parts in order, with explicit separators. Reject remote/file/content URLs without resolving or downloading anything. Receipt photos can contain multiple transactions; that is one image and one inference, returning the expense app's existing `receipts` array.
- Do not accept `response_format` as an enforced schema: return 400 `unsupported_response_format` if supplied. 10b selects Prompt-only JSON and omits that field. Do not silently imply constrained decoding.
- Per-request `temperature`, `top_p`, `top_k`, and `max_tokens` overrides return 400 `unsupported_parameters`. Use the loaded model's saved sampling settings, captured in each independent conversation; requests never mutate shared model configuration.
- Success uses the existing chat-completion envelope with string `choices[0].message.content`. Return only visible assistant output; omit thought channels, prompt echo, receipt bytes, and invented usage counts. The companion does not repair or certify receipt JSON; the expense app parses and validates it.

### Authentication and errors

Authenticate every retained route, including discovery, inference, health/model detail if retained, and any cancellation route. No server key means no authentication requirement. With a key configured, require exactly one valid `Authorization: Bearer <key>` header; reject missing, malformed, duplicate, or incorrect credentials with 401 before body decoding, model lookup, or inference. Validate configured keys against CR/LF/control characters and unsafe header values. Do not trim or transform a previously saved effective key differently between apps.

Return a stable envelope `{"error":{"code":"<code>","message":"<safe user guidance>"}}`. Use 400 for invalid request/image or unsupported features, 401 for authentication failure, 404 `model_not_ready` for absent/uninitialized models, 422 `vision_unavailable` for unsupported image inference, 429 `inference_busy` for failed admission, 413 for payload limits, 504 `inference_timeout` for the generation deadline, and 503 `runtime_unavailable` for startup/unload/runtime faults. Messages never include arbitrary exception text, request content, credential values, filesystem paths, or model output. These codes are the expense app's recovery mapping, not retry instructions; same-phone failures require explicit user retry.

### Request lifetime

Use a 180-second overall extraction deadline in the expense app, including client admission and all actual inference work. The companion independently stops generation within a maximum 180 seconds after accepting an inference; client cancellation should normally stop it sooner. Do not serialize by waiting an unbounded queue of expensive requests: atomic admission returns busy for competing inference.

The supported fork adds authenticated request-lifetime routes alongside OpenAI-compatible discovery/chat. These extensions are mandatory for this integration; Remote API profiles continue their existing protocol. Preparation and control are not inference and must remain available while generation owns admission:

1. `POST <base>/requests` with an empty object prepares one request and returns 201 with `instanceId` (a fresh UUID for this successfully started server), server-issued `requestId` (UUID), `expiresInMillis: 180000`, and `runtimeState: "available"`. Available means the coordinator has no quarantined/uncertain older generation; it does not claim a model is loaded, vision works, or another current-instance request is not busy. Preparation returns 503 if the runtime is quarantined or an earlier server lifetime has not safely settled. It does not allocate/load a model or start generation. Bound pending records, initially at 128; reject excess with 503 rather than evicting active work. The lifetime starts at preparation and cannot be extended by sending chat or polling.
2. The client sends these IDs as `X-Companion-Instance` and `X-Request-Id` on its single `POST /chat/completions`. After authentication, atomically claim an unexpired Pending record as Preparing before reservation/body processing. Only a Pending record in the current instance can be claimed once; cancelled, expired, unknown, reused, or old-instance IDs return 409 `request_not_active`. Preparation registration alone does not reserve generation admission; claimed chat acquires the global reservation with an immediate try, or becomes Drained and returns busy without decoding. Preparing covers body receipt/decode/resource ownership; transition to Generating only while reservation is owned and cancellation has not occurred. Claim/cancel/native-start transitions share one state boundary so a Stopping request cannot start late. Every success envelope includes the IDs as response headers and is emitted only after native terminal completion/resource drain.
3. `DELETE <base>/requests/<requestId>` with the instance header is idempotent cancellation. Unclaimed Pending work becomes Drained immediately, preventing later chat. Preparing or Generating work becomes Stopping: cancel body IO/decoder work, invoke native stop if it started, and await preparation/native cleanup plus reservation release. Return 200 with `{instanceId,requestId,state:"drained"}` only after all of that cleanup is confirmed; return 202 with `state:"stopping"` when acknowledgement is pending. `GET` reports Pending/Preparing/Generating/Stopping/Drained/Unavailable for bounded polling. A cancelled decoder cannot produce a late bitmap/native start; if preparation cannot settle, quarantine just as for hung generation. An unknown/expired record returns 404 and cannot assert drain; an instance mismatch returns 409.
4. Keep Drained tombstones for at least five minutes and expire unused Pending records at their fixed deadline. After record removal, chat with that ID is still rejected as unknown; never create records implicitly from chat. Duplicate cancellation cannot affect another request. Stop/restart invalidates IDs and cannot reactivate a cancelled record.
5. Freeze the server key for its running instance; settings apply on explicit Stop/Start. Client cleanup uses the captured endpoint/key/IDs, never the newly edited profile. Authentication still precedes control lookup; no-key control omits Authorization. Responses contain no credentials or expense data. A cancelled preparation whose reply was never received cannot have started generation and expires safely.

HTTP cancellation alone is not proof of native termination. C1 must prove both actual socket-close propagation and the client-observable control acknowledgement. Establish a real non-streaming socket-close observer that invokes `stopResponse` and awaits terminal callbacks, including abrupt client death where no DELETE is sent. If Ktor/Netty cannot provide this, implement and test a bounded connection lease/observer before C5/E5; the control routes alone do not satisfy disconnect behavior. Use an initial 10-second stop/drain bound; after an unconfirmed stop quarantine the runtime, report Unavailable, and prohibit new generation. Do not force-close a running native instance to simulate completion.

The expense operation's 180-second budget never extends for extraction results. Allow a separate bounded 10-second cleanup scope to cancel/poll without publishing a result; lack of confirmed drain blocks further same-phone inference and offers Stop/restart recovery. Instance mismatch/404/network failure is not a drain acknowledgement. A new Ready server instance may be used only after the companion's global runtime coordinator has settled or fenced all older work; recreating a service/instance ID cannot bypass quarantine. A fake transport or cancelled deferred cannot close this requirement. C1 is a blocking implementation gate until both apps agree on and test these semantics.

## 3. Design and code ownership

Keep HTTP DTOs/parsing separate from model execution and Android service/UI lifecycle. Proposed new classes under `openai/` are `ServerEndpointSettings`, `ServerSettingsRepository`, `ServerCredentialStore`, `ChatRequestParser`, `InlineImageDecoder`, `InferenceCoordinator`, and `CompanionInferenceAdapter`; names are implementation targets, not existing files.

- `OpenAiModels.kt`: custom string-or-array content serializer, request DTO validation, response DTOs kept string-compatible, typed error codes.
- `OpenAiServer.kt`: loopback bind, configurable route prefix, authentication before payload work, bounded reads, error mapping, request-owned cancellation, and inference-adapter invocation.
- `LlmChatModelHelper.kt` plus model-manager load/unload entry points: explicit initialized capabilities, observable reset failures, terminal generation signals, and coordinated cleanup. Inspect all callers before changing the helper interface.
- `OpenAiServerService.kt`: user-started foreground lifetime, truthful bind state, non-sticky restart behavior, stop/drain, and no tunnel or LAN-address discovery.
- `OpenAiServerState.kt` and `ui/server/ServerScreen.kt`: persisted endpoint settings, transient masked key entry/clear, active versus saved endpoint, separate service/model readiness, and explicit actions. Remove tunnel controls and prevent old preferences/intents from activating them.

Use a single process-wide inference coordinator shared by all server inference routes and companion chat/model UI paths that touch the same runtime. A per-model lock alone is insufficient for the chosen single-inference/device-memory policy. Lock ordering and ownership must be documented; do not hold a settings lock while waiting for native callbacks.

Acquire its atomic preparation/generation reservation after authenticating and validating the prepared request ID and minimal headers, before materializing a full request body or decoding any bitmap. Hold it through bounded read, decode, native generation, terminal drain and image disposal. Busy competitors return 429 without allocating image payloads; bound/discard their remaining transport input without buffering. Preparation/status/cancellation/discovery routes have their own small body limits and remain callable while the reservation is held. Impose a bounded body-read timeout within the fixed prepared-request lifetime so a stalled upload cannot monopolize the runtime. Companion chat/UI image preparation must use the same memory reservation or an explicitly bounded separate allocation budget; generation serialization alone does not bound concurrent decoded images.

Model lifecycle states: Unloaded → Loading → Ready(text/vision capability) → Generating → Ready; Unloading and Failed are explicit. An image request may enter only a Ready engine whose actual initialization recorded a vision backend and whose model supports images. A text-initialized vision-capable model requires a coordinated user-visible reinitialization before image serving, rather than changing `supportImage` during reset. Never infer capability from a filename alone.

Conversation lifetime is one request. Create/reset under admission, fail if reset fails, and close/reset after terminal completion. Do not replay past expense messages. Snapshot sampler options for the request instead of leaking mutations into later calls. Close decoded image resources only after native inference has finished using them.

# App View Separation Plan

Last updated: 2026-09-11

Status: ✅ Done

## Objective

Separate configuration and profile-management controls from the receipt workflow so the Android app has two focused destinations:

1. A **Main** screen for selecting the provider used by the next receipt, verifying that provider, checking OneDrive readiness, importing a receipt image, reviewing the extracted receipt, and confirming/exporting it.
2. A **Settings** screen for configuration that is not part of the normal receipt-processing path.

The separation must preserve the current provider-selection, extraction, review, OneDrive authentication, retry, and export behavior. It must not change the normalized receipt contract or the image-first OneDrive publication order.

## Current State

`MainActivity` currently owns dependency construction, activity-result launchers, screen state, background orchestration, and one vertically scrolling Compose layout. That layout contains:

- the complete model-profile selector, list, editor, and import/export controls;
- the Microsoft account and OneDrive controls;
- the oversized-image reduction preference;
- the receipt image picker;
- receipt extraction progress;
- receipt review and correction; and
- OneDrive export and retry.

The profile-management UI is already extracted into `ModelProfilesPanel`, but it is rendered inline on the same screen as the receipt workflow. There is no app-level navigation dependency or destination model yet.

## Target Information Architecture

### Main screen

The Main screen is the operational receipt workflow. Other than navigation chrome, it shall contain only:

1. **Selected profile**
   - A compact dropdown containing the local provider and all saved remote profiles that are eligible for selection.
   - A concise effective-provider summary showing which provider will handle the next extraction.
   - Selection changes apply only to the next extraction; an extraction already in progress continues with its immutable provider snapshot.
   - If remote providers are disabled in Settings, remote entries remain visible but cannot be activated. The UI explains that remote providers must first be enabled in Settings.

2. **Verify profile connection**
   - A button that verifies the currently selected saved remote profile without importing or transmitting a receipt.
   - The latest verification progress/result appears beside the selector and is scoped to the profile that was tested.
   - Verification must use the saved profile metadata and its secure credential alias, never an unsaved editor draft.
   - The action is disabled while selection is unresolved, another profile operation is running, or no supported remote profile is active.

3. **OneDrive status**
   - A compact readiness summary derived from `GraphAuthenticationUiState`.
   - It distinguishes initializing, signed out, interaction required, connected/unverified, verified, busy, and error states.
   - It retains actionable recovery messaging needed before export.
   - The exact placement of connect, reconnect, verify-folder, and disconnect actions is a decision point documented below.

4. **Receipt image import**
   - The existing Android Photo Picker action.
   - Extraction progress and actionable extraction failure messages.
   - Image-size reduction uses the persisted Settings value and is not editable on the Main screen.

5. **Receipt review, confirmation, and export**
   - Editable receipt date, merchant, amount, currency, and merchant location.
   - Extraction status, confidence, manual-entry recovery, and raw-output diagnostics.
   - Confirm and export, export progress, completion, and idempotent retry.
   - Export remains unavailable with an explanatory recovery path until OneDrive is ready.

6. **Navigation chrome**
   - A top app bar title and Settings icon are allowed even though they are not receipt-workflow content.
   - The Settings icon opens the Settings destination without clearing the current receipt review or export state.

### Settings screen

The Settings screen shall contain:

1. **Remote-provider controls**
   - The explicit remote-provider enable/disable switch.
   - The existing privacy disclosure explaining that remote testing and extraction contact the configured endpoint and may send receipt data.
   - The current effective-provider summary so a settings change has visible consequences.

2. **Saved profile management**
   - View saved profiles.
   - Add, edit, test, save, save-and-select, and delete a profile.
   - Input-mode and structured-output configuration.
   - Masked credential entry and explicit credential clearing.
   - Existing validation, test status, delete confirmation, and unsaved-change confirmation.

3. **Provider configuration transfer**
   - Export all saved provider profiles.
   - Select, validate, preview, and confirm a provider-profile import.
   - Preserve the current security boundary: no API keys, credential aliases, or persistence timestamps in an export.

4. **Receipt image preprocessing**
   - The `Reduce input images larger than 200 KB` preference and its explanation.
   - Changes are persisted immediately and affect the next receipt import, not an extraction already in progress.

5. **Navigation chrome**
   - A Settings title and Up/Back action.
   - System Back and the Up action return to the existing Main destination and preserve its current workflow state.
   - Leaving a profile editor with unsaved changes continues to require confirmation.

OneDrive destination paths, the receipt review form, receipt import, and receipt export do not belong on the Settings screen.

## Proposed Compose Architecture

Use a single-activity Compose application with two destinations. Add Navigation Compose and keep route names internal to the UI layer.

```text
MainActivity
└── SmartExpenseApp
    ├── main
    │   └── ReceiptWorkflowScreen
    │       ├── MainTopAppBar
    │       ├── CompactProviderSelector
    │       ├── OneDriveStatusCard
    │       ├── ReceiptImportSection
    │       └── ReceiptReviewEditor
    └── settings
        └── SettingsScreen
            ├── SettingsTopAppBar
            ├── RemoteProviderSettings
            ├── ModelProfilesPanel
            ├── ProviderConfigTransferActions
            └── ReceiptImagePreprocessingSettings
```

Recommended responsibilities:

- `MainActivity` constructs application dependencies and supplies the Compose root. It should no longer define the complete screen layout.
- `SmartExpenseApp` owns the `NavHost`, top-level destinations, shared ViewModel acquisition, and callbacks requiring Android activity-result APIs.
- `ReceiptWorkflowScreen` renders the Main screen from immutable UI state and emits user events.
- `SettingsScreen` renders settings/profile-management state and emits user events.
- `CompactProviderSelector` is distinct from `ModelProfilesPanel`; the former supports quick selection and selected-profile verification, while the latter owns full profile configuration.
- `OneDriveStatusCard` separates the compact Main-screen presentation from `GraphAuthenticationViewModel` and the existing authentication client.
- `ReceiptReviewEditor` moves out of `MainActivity` into the receipt UI package without changing validation or export semantics.

Avoid passing an entire ViewModel deep into reusable composables. Screen-level composables may bind ViewModels, but child components should receive state and callbacks. This keeps navigation and UI behavior testable with fake state.

## State Ownership and Lifecycle

### Model profile state

Keep `ModelProfilesViewModel` scoped above the two destinations so Main and Settings observe the same `ModelProfilesUiState` instance.

Add explicit ViewModel operations for the compact Main workflow rather than driving the profile editor indirectly:

- select the local provider;
- select a saved remote profile subject to the existing remote-enabled rule;
- verify the selected saved remote profile; and
- expose verification state keyed by profile ID.

The effective-provider summary must continue to come from `SelectedReceiptModelProviderResolver`, so the dropdown cannot display a remote provider as active when runtime resolution would fall back locally.

### Receipt workflow state

Move `extracting`, `exporting`, `reviewState`, and receipt workflow events out of local destination composition state into a lifecycle-aware receipt workflow state holder, preferably a `ViewModel`.

This state holder shall:

- survive navigation from Main to Settings and back;
- capture the selected provider and image-reduction preference at the start of extraction;
- prevent duplicate picker, extraction, or export actions while busy;
- retain the stable export ID needed for retry;
- keep receipt and raw model data out of persistent saved state unless a separately reviewed persistence requirement is added; and
- continue to run background work outside composable functions.

Navigation away from Main must not cancel a valid in-flight extraction or export solely because its composable left composition. Returning to Main must display the latest state.

### Settings preference state

Wrap the oversized-image `SharedPreferences` access behind a small settings repository/state holder. The Settings checkbox writes through that boundary; receipt extraction reads a snapshot when the user selects an image.

Do not read or write preferences directly from leaf composables.

### OneDrive state

Keep `GraphAuthenticationViewModel` shared and lifecycle-aware. The compact Main card observes the same state used by the authentication/export pipeline so readiness messaging cannot drift from actual export eligibility.

The export button should use a single derived readiness rule rather than comparing Graph status separately in several composables.

### Activity-result launchers

- Keep receipt Photo Picker launch/result handling in the app or Main-screen binding layer.
- Move provider configuration `CreateDocument` and `OpenDocument` launchers to the Settings binding layer.
- Treat picker cancellation as a no-op.
- Preserve current coroutine dispatching for document and image I/O.
- Do not retain an `Activity`, URI permission object, or launcher inside a ViewModel.

## Navigation Behavior

- The initial destination is Main.
- The Settings icon creates at most one Settings entry on the back stack.
- Up and system Back from Settings return to the existing Main entry.
- System Back from Main follows normal activity behavior.
- If the profile editor contains unsaved metadata or a newly entered API key, Back/Up first shows the existing discard confirmation. Confirming discard returns to the profile list; a second Back/Up leaves Settings.
- Opening Settings while receipt extraction/export is busy is allowed because the operation is owned above the destination. Settings actions that could conflict with an active operation remain governed by immutable extraction/export snapshots.
- Changing the selected profile or image-reduction setting never mutates an in-flight extraction.

## Risks and Mitigations

- **Navigation can discard locally remembered receipt state.** Move workflow state above destination composition and test a Settings round trip during review and busy operations.
- **The dropdown can disagree with actual provider fallback.** Render effective selection from the resolver and use one ViewModel operation for selection changes.
- **Quick verification could accidentally test stale editor data or transmit a receipt.** Verify only a saved-profile snapshot with the dedicated connectivity contract.
- **Moving the image preference can introduce timing ambiguity.** Snapshot the value when image import starts and apply changes only to subsequent imports.
- **OneDrive status can drift from export eligibility.** Derive both from one shared readiness rule backed by `GraphAuthenticationUiState`.
- **Back navigation can expose or lose an unsaved API key.** Reuse discard confirmation, keep the key only in ephemeral editor state, and clear it when the editor is discarded.
- **A broad `MainActivity` refactor can hide regressions in unrelated business logic.** Extract state and composables first, then introduce destinations, with tests after each phase.
- **Existing user work is already present in the working tree.** Implement this plan in focused changes that preserve unrelated modifications and avoid wholesale rewrites.

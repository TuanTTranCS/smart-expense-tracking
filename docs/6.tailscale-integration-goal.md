# Goal: Profile-Gated On-Demand Tailscale Access for LM Studio

Add optional Tailscale connect/disconnect controls to the Android receipt app so selected OpenAI-compatible model profiles can access LM Studio running on the Windows 11 mini PC through its Tailscale address.

The control must be explicitly enabled per model profile and must never appear or operate for profiles that do not permit it.

## Implementation Readiness

The intended behavior, data flow, and test areas are outlined below. Resolve these integration details before treating the goal as implementation-ready:

1. **Status semantics:** `CONNECT_VPN` and `DISCONNECT_VPN` are requests. The broadcast does not acknowledge delivery or expose authoritative Tailscale VPN state. Define what makes the control appear on/off after a request, on app restart, and when Tailscale is changed outside this app. Endpoint reachability alone cannot prove that Tailscale is connected because the same host may be reachable over a LAN.
2. **Readiness probe:** The probe method is now set: use the existing saved-profile connectivity test and its expected `{"status":"ok"}` success response, as described in section 5. It uses the selected saved profile’s credentials. Before implementation, still set the per-attempt timeout, retry interval, overall timeout, and whether the control supports every opted-in remote profile or only LM Studio profiles. LM Studio also documents `GET /v1/models`, but that does not replace the existing test for providers that require a model-specific response. [LM Studio model-list endpoint](https://lmstudio.ai/docs/developer/openai-compat/models)
3. **HTTP access:** The current [network security configuration](../android-app/src/main/res/xml/network_security_config.xml) permits cleartext HTTP only for `10.0.0.207`. A Tailscale IP or MagicDNS `http://` base URL needs an explicit Android network-security decision. A physical-device test has since confirmed the HTTPS endpoint described in section 5 works without adding a cleartext exception. Keep the endpoint in the saved profile.
4. **Target-device contract:** Verify the installed Tailscale package, receiver behavior, VPN consent/login flow, and reconnect behavior on the target phone. The linked Android 16 issue reports behavior from one development build, so its two-broadcast workaround is not a general requirement.

Current repository versions are Room `ModelProfileDatabase` v1 and provider-configuration JSON v1. An implementation should migrate the profile database from v1, export its new Room schema, emit provider-configuration v2, and continue accepting v1 imports with the new flag defaulting to `false`.

## Functional Requirements

### 1. Per-profile Tailscale permission

Add a persisted Boolean capability to every saved remote `ModelProfile`, for example:

```kotlin
val showTailscaleToggle: Boolean = false
```

The default must be `false`.

The option must:

- Appear in the existing remote profile editor in Settings.
- Be saved and restored with the profile.
- Be editable independently for every profile.
- Not be stored in global `AppSettings`.
- Not affect provider selection or remote-provider opt-in.
- Not automatically connect or disconnect Tailscale when changed.

Suggested UI text:

```text
Show Tailscale control on Main
```

Supporting text:

```text
When this profile is selected, show a control for connecting to the Tailscale network used by its model endpoint.
```

The built-in local `On-device Gemma` provider has no Tailscale option.

### 2. Main-screen visibility rule

Show the Tailscale control on Main only when all conditions are true:

1. The effective selected provider is an OpenAI-compatible remote profile.
2. Remote providers are enabled.
3. The selected profile still exists.
4. That profile has `showTailscaleToggle == true`.

Otherwise:

- Do not show the Tailscale connect/disconnect control.
- Do not allow Tailscale actions through callbacks, ViewModels, or services.
- Selecting the local provider must hide the control.
- Selecting a remote profile with the option disabled must hide the control.
- Disabling remote providers must hide the control because the effective provider becomes local.

The rule must be enforced in state/action handling, not only by hiding the Compose component.

### 3. Tailscale control behavior

Add a small Main-screen card or row near the provider selector.

The control should show:

- Tailscale request and endpoint-readiness status; show VPN state only if a reliable source is available.
- The selected profile name or model endpoint it applies to.
- A connect/disconnect `Switch` or equivalent toggle.
- An actionable error when Tailscale is unavailable or the LM Studio endpoint cannot be reached.

Suggested states:

```text
Disconnected
Connecting…
Connected — LM Studio reachable
Disconnecting…
Connection requested
Unavailable
Error
```

The control is bound to the currently selected profile. A profile change must recalculate visibility and permission immediately.

Do not automatically disconnect Tailscale after extraction. The user may leave it connected and may disconnect it manually from the Main screen or Tailscale itself.

### 4. On-demand connection flow

When the user turns the control on:

1. Confirm that the current effective provider still permits Tailscale control.
2. Send a package-targeted Android broadcast to the installed Tailscale app.
3. Target package: `com.tailscale.ipn`.
4. Use the supported actions:
   - `com.tailscale.ipn.CONNECT_VPN`
   - `com.tailscale.ipn.DISCONNECT_VPN`
5. Poll or retry the selected profile’s LM Studio connectivity until it succeeds or a bounded timeout is reached.
6. Do not use a fixed delay as the readiness check.
7. Once the endpoint is reachable, show readiness. Receipt extraction continues through the existing provider pipeline; specify separately if the UI should block extraction while readiness is pending.

The current Tailscale Android manifest exposes these broadcast actions through `IPNReceiver`; treat this as a version-sensitive integration point and validate it against the installed Tailscale version on the target phone. [Current Tailscale Android manifest](https://github.com/tailscale/tailscale-android/blob/main/android/src/main/AndroidManifest.xml)

An Android 16 report describes a reconnect failure after another VPN took over, using a Tailscale development build and Tasker. It reports a second `CONNECT_VPN` intent after approximately two seconds as part of its workaround. Do not make that workaround unconditional; verify the installed version and device behavior first. [Tailscale Android 16 reconnect issue](https://github.com/tailscale/tailscale/issues/18847)

### 5. Connectivity verification

Reuse the selected saved profile’s existing endpoint and credential configuration.

Do not send receipt images or receipt text merely to determine whether Tailscale is ready.

Use the existing saved-profile connectivity test as the supported non-receipt probe. It uses the saved profile’s endpoint, model, output format, and credential configuration, and validates the expected `{"status":"ok"}` response. Do not use receipt image or receipt text for readiness checks.

The probe must use the immutable selected-profile snapshot and must not use unsaved editor data.

The bundled LM Studio profile currently has a LAN-style default URL. A physical Pixel 7 test confirmed that, with the mini PC and phone connected to the same Tailscale network, LM Studio serving its endpoint, and LM Studio’s **Allow local network access** enabled, the mini PC’s Tailscale Serve HTTPS URL works as the profile `baseUrl` both on the local network and on an external network:

```text
https://<MINI_PC_NAME>.<TAILNET_NAME>.ts.net/v1
```

The `/v1` URL uses the Tailscale Serve HTTPS endpoint and omits LM Studio’s `:1234` port. Save this full URL in the existing profile `baseUrl`; do not hard-code a separate Tailscale endpoint into the toggle feature. Keep the bundled LAN default unchanged unless the user chooses to edit it. The phone-side test confirms endpoint reachability but does not by itself report authoritative VPN state.

### 6. Disconnect flow

When the user turns the control off:

1. Re-check that the currently selected profile still permits Tailscale control.
2. Send `com.tailscale.ipn.DISCONNECT_VPN` to `com.tailscale.ipn`.
3. Update the UI to a request-sent or disconnecting state. Do not claim the VPN is disconnected solely because the broadcast was sent.
4. Handle missing Tailscale installation, broadcast dispatch failures, competing VPNs, and timeout states without crashing.
5. Do not disconnect automatically when selecting another profile or the local provider.

Because the external broadcast is not itself a complete authoritative VPN-state API, distinguish between:

- Command dispatched/requested (delivery and acceptance are unconfirmed).
- Tailscale state confirmed, only if a reliable observable source is available.
- LM Studio endpoint reachable.
- LM Studio endpoint unavailable.

## Data and Persistence Changes

Update the profile domain and persistence layers:

- Add the Boolean capability to `ModelProfile`.
- Add it to `ModelProfileDraft`.
- Add it to `ModelProfileEntity`.
- Add a Room migration from `ModelProfileDatabase` v1 to v2 with a default value of `false`, and export the v2 schema.
- Preserve the value through repository save, edit, selection, and deletion flows.
- Existing migrated profiles and the bundled LM Studio profile must default to `false`.
- Do not change the selected profile or remote-provider opt-in during migration.

## Provider Configuration Transfer

The Tailscale capability is profile metadata and must be included in provider configuration export/import.

Recommended approach:

- Emit provider configuration schema v2 while retaining v1 import support.
- Export the Boolean field for each profile.
- Accept older configuration files and default the field to `false`.
- Preserve the existing rules:
  - Credentials are never exported.
  - Imports are validated and previewed.
  - Imports are atomic.
  - Conflicting profile IDs are copied.
  - Current selection and remote opt-in remain unchanged by import.

## Suggested Architecture

Add a small Android-side abstraction, for example:

```kotlin
interface TailscaleController {
    fun requestConnect(profile: ModelProfile)
    fun requestDisconnect(profile: ModelProfile)
    fun observeStatus(): Flow<TailscaleStatus>
}
```

The controller should not independently decide whether a profile is allowed. The ViewModel or use-case layer must first resolve the effective selected provider and enforce:

```text
effective provider is remote
AND selected profile exists
AND selected profile.showTailscaleToggle == true
```

The controller should receive only a saved, immutable profile snapshot.

Keep Tailscale orchestration separate from:

- Receipt extraction.
- OneDrive authentication.
- Receipt export.
- Global app settings.
- The local Gemma provider.

## Tests

Add focused coverage for:

### Shared JVM tests

- New profile capability defaults to `false`.
- Profile copies preserve the capability.
- Profile-to-provider conversion preserves the capability where needed.
- Old provider configuration imports default the capability to `false`.
- New provider configuration export/import preserves the capability.
- Resolver exposes Tailscale permission only for the selected effective remote profile.
- Local fallback never grants Tailscale control.

### Android unit tests

- Room migration adds the new field with `false`.
- Profile editor save and edit preserve the field.
- Legacy migration defaults the field to `false`.
- ViewModel rejects connect/disconnect actions for:
  - The local provider.
  - A disabled remote provider.
  - A missing selected profile.
  - A profile whose capability is disabled.
- ViewModel forwards actions only for the currently selected eligible profile.
- Profile changes invalidate or cancel stale connection operations.
- Connect retries until endpoint readiness or timeout.
- Receipt data is never sent by the connectivity probe.

### Compose UI tests

- Settings shows the per-profile Tailscale checkbox.
- Main shows the control for an eligible selected profile.
- Main hides it for the local provider.
- Main hides it when remote providers are disabled.
- Main hides it for a profile with the option unchecked.
- Switching between profiles updates visibility.
- The control exposes accessible labels and status text.
- Busy, connecting, disconnecting, and error states are rendered correctly.

### Physical-device verification

On the target Android phone:

1. Install and authenticate Tailscale.
2. Configure the mini PC and phone in the same tailnet.
3. Configure the LM Studio profile’s `baseUrl` as `https://<MINI_PC_NAME>.<TAILNET_NAME>.ts.net/v1` (the HTTPS Tailscale Serve URL, without `:1234`); keep LM Studio **Allow local network access** enabled on the mini PC.
4. Enable “Show Tailscale control on Main” for that profile.
5. Select the profile on Main.
6. Connect Tailscale from the app.
7. Wait for the LM Studio endpoint to become reachable.
8. Extract a receipt through the existing workflow.
9. Disconnect Tailscale from the app.
10. Select the local provider and confirm that the Tailscale control is unavailable.

The URL and reachability setup in step 3 were manually verified from a physical Pixel 7 on both a local and an external network on 2026-09-29. The remaining steps, including app-driven Tailscale commands and readiness UI, are still pending implementation and device verification.

## Definition of Done

- The capability is persisted per remote model profile.
- The option is editable only in Settings.
- Main shows the Tailscale control only for the currently selected eligible profile.
- Local providers and disallowed profiles cannot trigger Tailscale actions.
- LM Studio access uses the profile’s existing OpenAI-compatible endpoint.
- Connection readiness uses bounded reachability retries rather than a fixed delay.
- No router configuration, port forwarding, SSH tunnel, Tailscale Funnel, or Always-on VPN is required.
- Existing extraction, review, OneDrive export, profile selection, import/export, and local fallback behavior remain intact.
- Unit tests and Compose tests cover the new behavior.

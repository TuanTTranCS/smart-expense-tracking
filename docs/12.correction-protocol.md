# Correction protocol v1

The consumer must run this version before app re-export is enabled. The app gates
editing publication on `logs/receipt-correction-capabilities.json` containing
`correctionProtocolVersion: 1`, `enabled: true`, `acknowledgements: true`.
Normal consumer runs publish this capability; dry runs do not write it.

## Immutable operations

Publish one UTF-8 JSON object, with create-only final filename
`logs/expense_correction_<operationId>.json`. UUIDs use lowercase canonical D format.
Never modify an original singleton, batch, expanded list, archived handoff, or an
existing correction operation. Temporary files must not end in `.json`.

```
{
  "correctionProtocolVersion": 1,
  "operationId": "00000000-0000-4000-8000-000000000001",
  "expenseId": "00000000-0000-4000-8000-000000000002",
  "expectedRevision": 0,
  "expectedPayloadJson": "<exact prior expense object encoded as a JSON string>",
  "expectedPayloadSha256": "<lowercase SHA256 of UTF8 expectedPayloadJson, no BOM>",
  "payload": { "...": "complete corrected Version 2 or 3 expense" }
}
```

`expectedPayloadJson` avoids cross-runtime canonical-number/escaping hashes.
The consumer verifies its SHA256, parses it, and separately compares its JSON
value with the durable prior payload. Property order and whitespace are immaterial
to that second comparison. Unknown JSON fields survive in the complete payload.
The app retains remote unknown fields when creating corrections.

The payload retains ID, creation timestamp, source device/provenance and image
references. It uses `extractionStatus: manual` and explicit `itemType: pending`
or `processed`. New originals use pending; missing itemType means legacy pending;
unsupported values fail validation. A standalone processed object cannot insert.

Originals have revision 0. A successful correction increments revision by one.
Order operations by expectedRevision, then filename. Two conflicting operations
with one expectedRevision cannot both apply. Reuse the same immutable operation
and bytes for retry; further changes require another operation ID.

## Pending processing and races

After atomic batch validation/expansion, the processor takes a pending operation
as an in-memory overlay only when the original member is present, its prior JSON
matches, its revision is zero, and there is no competing pending operation for
that member. It journals the overlay before workbook processing. Original queue
and batch bytes remain unchanged. Successful insertion publishes revision 1 and
acknowledges the operation. Quarantined originals do not establish application.

A pending correction received after original processing returns conflict with
`reasonCode: processing_changed`; publication is not application. The app keeps
the edit and refreshes. An explicitly confirmed processed operation with a new
operation ID is required. Missing original bytes/row identity defer; the consumer
never inserts a correction as an independent expense.

## Public status and acknowledgements

`logs/receipt_correction_state/<expenseId>.json`:

```
{"correctionProtocolVersion":1,"expenseId":"<UUID>","revision":0,
 "payload":{},"status":"processed","operationId":"<only after correction>"}
```

Written after a durable original insertion/state completion, and after each
correction. Existing v1 processor records migrate conservatively using their
exact archived original and recorded row; no guessed historical row mapping.
Absent public state can be resolved as revision 0 only with the recorded archive.
An exact-duplicate/shared row is ineligible for automatic correction.

`logs/receipt_correction_acks/<operationId>.json`:

```
{"correctionProtocolVersion":1,"operationId":"<UUID>","expenseId":"<UUID>",
 "status":"applied|conflict|deferred","reasonCode":"updated","expectedRevision":0,
 "revision":1,"processedAt":"<UTC timestamp>","payload":{}}
```

Only `applied` confirms Excel application. `payload`, when present, is the durable
current payload. The app compares operation/expense identity and confirmed payload;
it must never promote upload success, missing files, folder membership, stale
status or a deferred/conflict acknowledgement to application. Deferred operations
remain retryable; conflict requires refreshed review and a new operation.

## Workbook journal and replay

The machine-local processed-expenses state migrates v1 to v2 while preserving
existing records. Each record stores `appliedRevision`, complete `currentPayload`,
and the last applied `operationId`. A top-level `operations` map stores immutable
operation snapshots and their acknowledgements. This local ledger is authoritative;
OneDrive status files are projections, repaired from local state on normal runs.
Missing legacy archives remain ineligible rather than acquiring guessed payloads.
Identical applied or conflict operations stay quiet on subsequent runs; a missing
public acknowledgement is regenerated from the durable ledger, including when
the operation file has already been archived. ID reuse with
different content is rejected and cannot replace the original acknowledgement.

## Correction queue lifecycle

Hermes archives an applied `expense_correction_<operationId>.json` under
`logs/receipt_jsons_done/`, preserving its filename and exact bytes. This also
applies to corrections consumed as pending-original overlays. The order is:
durable workbook save, durable local operation/revision state, public current
state and `applied` acknowledgement, then archival. Folder membership never
replaces acknowledgement and revision validation in the app.

Terminal conflicts go to `logs/receipt_jsons_review/`; malformed or invalid
operations go to `logs/receipt_jsons_error/`. Both retain an actionable sidecar
reason without copying full receipt payloads into diagnostics. Deferred
operations stay in the inbox and remain eligible for retry. Temporarily missing
dependencies must remain retryable.

An archive failure after application must preserve the applied operation and its
acknowledgement. A later run retries archival without applying the Excel change
again. An existing destination with identical bytes may complete a proven
terminal operation; a destination with different bytes must never be overwritten.
Normal runs also archive terminal operations left in the inbox by older versions.
Dry runs do not move files, publish acknowledgements or persist notification state.

For publication retries, the Android app reconciles matching operation content in
the terminal archive folders as well as the inbox. If public state identifies the
operation while its archive and acknowledgement lag, retain the saved retry.
Neither observation alone confirms Excel application; await its acknowledgement.

Hermes reports the first deferral for an immutable correction operation, then
suppresses repeated notifications while its deferred reason is unchanged, even
across restarts. Suppression does not stop processing or acknowledgement repair.
A changed deferred reason or a terminal outcome is reportable. Quiet retries do
not add reportable item/count entries, so a run containing only unchanged
deferrals renders `[SILENT]`.

Original expense handoffs use a separate machine-local
`<StatePath>.notification-state.json` cache keyed by filename and content hash,
with deferred reason/diagnostic identity. This cache affects notification output
only; the financial ledger and workbook retry decisions remain independent.

The adjacent `<StatePath>.correction-journal/<operationId>.json` stores the full
immutable operation, source/target row, expected F:H values and prepared phase.
It is written before workbook save and retained after success. Public revision
and acknowledgement are published only after workbook and row state save.
Replay checks journal identity and recognizes the saved after-state before any
second write, recovering a crash between workbook save and state/ack writes.

Verify old amount, description, image text, hyperlink and absence of formulas
before writing. Reject independently changed cells, duplicate targets, exact
duplicate legacy ownership, and rows shared by another expense ID. Same-month
changes touch F:H. Cross-month changes prepare an empty safe target, write its
F:H and clear source F:H in one workbook save; unrelated cells/formulas remain
untouched. Creating a monthly sheet and extending summary coverage follow the
existing consumer rules. An uncertain workbook save is reconciled from the
journal and actual cell contents; it is never assumed applied.

Pending original insertion journals its chosen unique row before workbook save.
A crash before the original state write recovers ownership only when that prepared
row uniquely matches the corrected cells. A prepared journal alone cannot claim
an original processed meanwhile with its original payload. Unknown JSON fields
are compared recursively; numeric lexical variants are equal, and array order,
null members, nesting and field values are preserved. Blank-result formulas count
as independent content in source and target cells and block correction.

Consumer and installed wrapper deployment do not change the production workbook,
queue or scheduled-job configuration. A later existing scheduled run publishes
the capability marker. Only disposable workbooks/queues are used for validation.

## 1. Current code and change boundaries

The repository was inspected on 2026-10-10. Existing reusable seams:

- `src/main/kotlin/com/hugo/smartexpense/extraction/ModelSelection.kt` defines two execution types, local and OpenAI-compatible, and requires remote opt-in for every saved API profile. `ModelProfile.kt` has no category and stores the selector as `selectedRemoteProfileId`.
- `OpenAiCompatibleReceiptModelClient.kt` already sends photos as text/image_url arrays and typed drafts as strings. It always requires an API key, supports only JSON Schema/Object, tests success by exact serialized text, and has JSON-schema recovery that can send a second request.
- `BatchRequestScheduler.kt` uses a local/remote Boolean policy, a shared request-start gate, a global three-slot outbound budget, and operation-scoped lazy credential capture. Verification reserves all three outbound slots. The existing extraction deadline is 180 seconds; retryable network/429/5xx failures can currently trigger automatic retries.
- `android-app/.../AndroidOpenAiCompatibleApiTransport.kt` uses cancellable `HttpURLConnection`, 10-second connect and 60-second read timeouts. Extraction does not explicitly disable redirects and reads the response without a size cap.
- `android-app/.../modelprofile/` provides Room v2 metadata, secure `AndroidApiKeyStore`, atomic import/conflict copying, duplicate-profile compensation, discovery, saved/editor verification, and generation-token invalidation. `ProviderModelCatalogService` delegates GET to the existing optional-key, bounded, redirect-rejecting models checker.
- `android-app/.../receipt/ui/ReceiptWorkflowViewModel.kt` schedules a batch using `onDevice = profile == null` and treats any saved profile as remote for consent revocation. Update both decisions for explicit category.
- `android-app/src/main/res/xml/network_security_config.xml` narrowly allows the existing remote development host `10.0.0.207`; add a separate literal-loopback rule without a global cleartext allowance.

Paths abbreviated as `android-app/.../` above are beneath `android-app/src/main/kotlin/com/hugo/smartexpense/app/`. Inspect all affected callers/tests before edits. Do not change batch/export Room v4 or Version 2 image/Version 3 typed handoffs; profile Room v3 and configuration-transfer v3 are independent version lines. ## 2. Domain, selection, and migration decisions

Add explicit API profile category `REMOTE_API` or `SAME_PHONE_SERVER`, propagated through `ModelProfile`, draft, provider option, selected provider, resolver, DAO/entity conversion, transfer DTO, and immutable operation snapshot. Represent Built-in on-device explicitly in selected-provider state; keep protocol/client reuse independent of inference location. Existing `ModelProviderType.OPENAI_COMPATIBLE_API` can remain the transport discriminator, but it must never serve as the remote-consent or scheduling discriminator.

Add `RemoteStructuredOutputFormat.PROMPT_ONLY_JSON`. Same-phone profiles require `DIRECT_IMAGE`, Prompt-only JSON, and `showTailscaleToggle = false`; typed drafts still use string content. Validate these combinations at save/import/request boundaries; do not infer category from a URL or silently coerce an invalid import.

Retain the stored selector column `selectedRemoteProfileId` in this migration to preserve its bytes and reduce schema changes; document it as a legacy name for a selected API-profile ID. Domain/UI naming may use selected API profile terminology. Resolution rules:

1. No selected ID, missing/deleted profile, or Built-in selection → Built-in on-device; no implicit inference is dispatched.
2. Same-phone saved profile → eligible independently of remote opt-in.
3. Remote API saved profile → eligible only with remote opt-in; otherwise Built-in.
4. Create, save, import, duplicate, discovery, and verification do not auto-select or auto-enable remote access.
5. Disabling remote opt-in clears selection only if the selected profile is Remote API and cancels only active/pending Remote API inference. Same-phone and Built-in work/selection survive that consent change.
6. A stopped server, auth failure, unavailable/non-vision model, invalid response, or timeout keeps the selected profile and draft/review state. Retry/manual entry is explicit; it never triggers fallback extraction.

Room migration `MIGRATION_2_3` adds a non-null category column with default `REMOTE_API`, exports schema 3, and retains existing output-mode values, timestamps, aliases, flags, selector ID and opt-in. Register both 1→2 and 2→3; test the chain and clean v3 creation. No destructive migration or key rewrite is permitted. Unknown corrupt category values must fail safe without dispatch, with an actionable configuration repair state.

Provider configuration v3 includes category and output mode, preserving existing fields and selector snapshot. Accept v1/v2 as Remote API with old output modes and v1's false Tailscale default, even for old loopback URLs. V3 rejects unknown categories/modes, illegal category capabilities, and invalid same-phone endpoints; never export/import keys, aliases, or timestamps. Use existing SAF preview/atomic import/conflict-copy logic and keep current device selection/opt-in unchanged. A credential-free same-phone import is valid; a key-enabled companion may return 401 later.

## 3. Endpoint, credential, and HTTP contract

Use the version 1 contract in 10a section 2 and identical golden fixtures. Same-phone endpoints use HTTP, exact literal host `127.0.0.1`, explicit port 1–65535, and a nonempty normalized API base path. Defaults are `http://127.0.0.1:8080/v1`; a custom example is `http://127.0.0.1:8091/expense/v1`.

The fork's mandatory request-lifetime extension applies only to Same-phone server: prepare with `POST <base>/requests`, capture server-issued request/instance IDs, send them on chat as `X-Request-Id`/`X-Companion-Instance`, and use authenticated DELETE/GET of `<base>/requests/<requestId>` for cancellation acknowledgement. Preparation/control never perform inference or use the generation permit on the server. A successful chat response confirms native drain and carries matching IDs; reject mismatched identities before publishing. Preparation, chat, and any result processing share the original client 180-second deadline; the server's fixed prepared-request expiry cannot restart it. Store IDs/keys only in the active in-memory operation.

Implement a category-aware endpoint value/validator shared by save/import/discovery/verification/extraction. Require the lexical authority to be exactly `127.0.0.1:<decimal port>` rather than relying on DNS or equivalent parsed addresses. Reject localhost, IPv6, alternate numeric loopbacks, zero/out-of-range/missing ports, user-info, query/fragment, LAN/remote hosts, scheme changes, backslashes, percent-encoded host/path, dot/traversal segments, repeated slashes, and root/empty API path. Match 10a's ASCII path grammar and trailing-slash normalization. Valid requests append `/models` or `/chat/completions` to the preserved prefix. Perform validation again immediately before request construction, including against imported/corrupt metadata.

Add only `<domain includeSubdomains="false">127.0.0.1</domain>` with cleartext permitted in the Android security config. Preserve the existing remote rule. Set `instanceFollowRedirects = false` for same-phone POST and GET operations, fail on every 3xx, and never forward a key. A category-approved URL is part of the transport request context, so verification/extraction cannot bypass the guard through a generic factory.

Credential editing uses Keep, Replace(nonblank value), or Clear, distinct from a blank text box. Unsaved editor operations use the draft's effective key intent; saved verification/extraction use saved key state. Clear must suppress use of a previously stored key during editor discovery/test, and successful save must durably remove the stored alias value. Failure to read/remove/save a credential is an error, not successful no-key configuration. A stable alias without a stored key is valid only for same-phone; Remote API retains current required-key behavior.

Freeze category, endpoint, model, input/output mode, and effective credential once at operation admission before queued batch work. All items/recovery calls use that immutable in-memory credential value; lazy first-use capture is insufficient if a key changes while items are queued. Never save secrets in Room, transfer files, batch snapshots, UI saved state, raw exception messages, or Debug output. Keep/Replace/Clear and transient masked entry require discard confirmation under the existing editor navigation rules.

Introduce one `ProfileConfigurationCoordinator` for metadata/key mutations and snapshot capture. All save/clear/delete/duplicate/import and saved discovery/verification/extraction admission paths use its short critical section; no HTTP or model work occurs while it is held. Read selector/profile metadata consistently and capture its effective key within that same boundary. Active operations retain the old complete metadata/key tuple; later operations see the committed new tuple, never an old endpoint with a replacement key.

For Replace, stage the key durably under a fresh alias owned by that profile revision, then atomically publish metadata referencing it. For Clear, publish metadata referencing a fresh credential-free alias. Keep retains the saved alias. Existing aliases/keys are preserved by migration; revision aliases remain distinct per profile. Do not overwrite the currently referenced alias before metadata commit. On commit failure or ambiguity, verify actual Room references before compensating; never remove a possibly committed key. After successful publish, remove the old unreferenced alias durably; deletion similarly removes metadata/selection before credential cleanup. A failed cleanup is reported as pending, never as successful secure clearing.

Use a small durable non-secret mutation/cleanup journal in profile Room v3 (alias/profile IDs and phase only) to recover crashes between staging, commit, and old-alias removal. Record staging intent before the secure write; commit the new metadata and cleanup intent transactionally. Recovery uses reference checks under the coordinator, cleans only journal-owned unreferenced aliases, and preserves uncertain referenced credentials for explicit recovery. Add its exported schema/migration coverage in E1. No key value enters the journal, and no broad secure-store scan is introduced. Failures retain actionable state without silently switching authentication off.

With no same-phone client key, omit Authorization entirely. Otherwise send Bearer for discovery, saved/editor verification, and extraction. Validate header-safe values; never send an empty/placeholder key. Server key settings are independent: missing/wrong client key gives actionable 401 guidance to align or explicitly clear keys in the two apps. An unknown server key is never guessed or downloaded.

Prompt-only JSON omits `response_format` for typed/photo/verification paths while retaining their existing prompts. Do not add a schema-recovery request when the field was already absent. JSON Schema/Object keep current remote contracts. Verification parses one strict JSON object and requires the expected `status: "ok"` semantic value rather than identical whitespace/order; reject extra fields, wrong types/status, arrays, prose, malformed JSON and trailing garbage. Verify readiness separately from GET models and from real photo/model quality.

Apply 10a's initial resource limits: 12 MiB UTF-8 request, one JPEG/PNG inline image of at most 8 MiB decoded bytes/16 megapixels/8192 maximum dimension, and 1 MiB UTF-8 response. Check known staged metadata before base64/body allocation and bound transport response reads. Extraction resizing disabled may require enabling preprocessing/reselecting an oversized receipt; keep the draft/image and show guidance. Do not change the strict sub-200-KB export image requirement.

## 4. Scheduling, deadlines, cancellation, and recovery

Replace Boolean policy eligibility with category-aware policy:

- Built-in on-device: concurrency one, no remote spacing; retain its existing inference behavior.
- Same-phone server: concurrency one, no remote spacing, 180-second operation deadline, no automatic network/busy/5xx retry; explicit item retry takes a new provider/input snapshot. Prompt-only JSON does not trigger schema recovery.
- Remote API: preserve configurable concurrency 1–3, default one, default 3.5-second start spacing, existing cooldown/recovery rules, and explicit consent.

Use a shared same-phone inference permit across batch, single-item Extract/Retry, and editor/saved verification, including separate profiles that point to the same companion. Do not rely only on each batch's semaphore. Discovery GET is not inference and does not acquire a generation permit. The global maximum of three active item requests remains. Separate same-phone and remote timing gates so an unrelated remote cooldown cannot delay same-phone work. Audit `InferenceExecution.request`'s outside-scope verification fallback, which currently imposes 3.5 seconds without category context.

Start the 180-second deadline before admission wait/dispatch, measure remaining budget monotonically, and clamp connection/read work to it. Same-phone read timeout must allow valid responses past the old 60-second cutoff, up to the remaining extraction deadline; no retry/recovery may restart the overall clock. Verification uses an explicit bounded inference context under the same permit, with the same native cancellation contract.

For a batch, start each item's clock when it becomes eligible for dispatch and enters its category admission attempt, after the previous same-phone item has completed/drained. Time merely queued behind earlier batch items does not consume that item's 180 seconds. Once an item begins that attempt, shared-permit waiting, request preparation, connection, generation, parsing, and all recovery consume the one deadline. Thus three slow serial items may take more than 180 seconds in total without timing out undispatched items. Freeze the run's provider/credential snapshot at Extract all; per-item deadline timing does not defer snapshot capture. Test both a slow multi-item run and a verification/retry that consumes its budget waiting for admission.

On removal, Cancel remaining, app backgrounding, timeout, editor stale verification, or applicable Remote API consent revocation: stop queued work, disconnect active HTTP, await adapter cleanup, and preserve completed results. Existing run/item/revision identity checks reject late completions. For same-phone cancellation, run idempotent DELETE then bounded GET polling in an explicit cleanup scope using captured endpoint/key/IDs; control work bypasses inference admission so it can stop its owner. Keep the client permit until a matching Drained acknowledgement, or quarantine same-phone dispatch if cleanup cannot confirm it within 10 seconds. Cap control connect/read attempts by the remaining cleanup budget. This cleanup can finish after the result deadline but can never publish extraction output.

Cancel-before-chat must drain a prepared Pending ID; late chat with that ID fails. If preparation was cancelled without returning IDs, no generation was possible. Treat 404, old-instance 409, failed authentication, and network failure as unconfirmed cleanup, never as proof of drain. Explicit Stop/restart recovery can clear client quarantine only when a preparation response reports a different server instance and `runtimeState: "available"`, governed by the companion's global no-old-generation fence; consume that identity only in the user's explicit retry, never silently resubmit an expense. Same-instance preparation alone cannot clear uncertain client state. Abrupt client death still requires the companion's independent disconnect observer/lease proved by C1. Socket close alone does not acknowledge cross-process cleanup.

Map stable companion error codes from 10a to guidance: start the stopped companion; load/reinitialize a vision model; finish/stop busy work; align optional keys; correct endpoint; reduce oversized input; retry a timeout; or manually correct invalid output. Do not display an arbitrary server error body verbatim: sanitize/redact credentials before Debug or user messages. Preserve source drafts, staged bytes, original typed notes, successful other items, edited reviews, and immutable export identities. Failed retry retains prior review for recovery while preventing stale export.

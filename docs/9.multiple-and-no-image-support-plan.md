## Goal and Scope

Let users prepare a batch containing receipt images, typed expenses without images, or both. Image input remains the default. Selecting files prepares previews only; the selected LLM is called after the user chooses **Extract all** or a no-image card's **Extract / Retry extraction** action. Each input owns a collapsible group containing its source review, extraction status, editable results, debug output, and export status.

Preserve the existing Kotlin, Compose, Room, coroutine, provider-selection, validation, and explicit remote opt-in architecture in [PLAN.md](PLAN.md). Follow the existing image viewer and retry behavior in [5.image-review-plan.md](5.image-review-plan.md) and [7.retry-extraction-plan.md](7.retry-extraction-plan.md), adapting their single-image ownership to individual batch items.

Include downstream image-free export in the implementation scope: at planning time, the Android exporter and production Windows processor required a paired image. The completed changes add explicit typed support throughout the OneDrive-to-Excel workflow.

## Input and Review Experience

### Multiple-image preparation

1. Change **Choose receipt** to **Choose images** and use `PickMultipleVisualMedia` with `ImageOnly`. A single selected image remains a valid batch.
2. Append the returned images in picker-return order, assigning a stable item ID to each. Canceling the picker leaves the existing batch unchanged.
3. Prepare each image asynchronously using the current preprocessing setting. Display loading/error state independently. Preparation must make no LLM request, including provider verification or OCR-based inference.
4. Show the exact processed image that will be sent to the model. Retain the current zoom/pan and accessible zoom controls for inspection before extraction.
5. Each thumbnail has an accessible **(×)** action, such as `Remove image 2`. The full-image review screen has a visible **Remove** action. Both remove the same item and its unexported results; neither deletes the original photo.
6. Provide **Add more** to append one or more images to the same batch. Existing previews, results, edits, and item IDs stay intact. Re-selecting an identical URI already present should show a duplicate-selection message and skip it; do not claim to detect identical photos with different URIs.
7. **Extract all** processes eligible, unprocessed items only. It is disabled for an empty batch, while a run is active, or while included image inputs are still preparing. A typed item needs some expense text in any source field; no individual field is required. The untouched CAD default alone does not constitute expense text. Nonblank free text must not be rejected because of its field placement, type, syntax, or format. Unreadable images require removal or reselection.
8. Display a batch summary such as `2 of 5 completed · 1 processing · 2 queued` and update each group as it finishes. No automatic export follows extraction.
9. After completion, **Add more** can extend the same batch. A later **Extract all** processes only new/changed inputs. Failed items expose an explicit **Retry extraction**; successful items are not silently extracted again.

Proposed initial resource bound: 20 input items per batch, counting both image and typed items. This is separate from the maximum concurrent request count of three. Keep the bound centralized and tune it after device testing; show the limit and explain rejected additions rather than silently dropping them.

The Android photo picker supports multi-selection and falls back to `ACTION_OPEN_DOCUMENT`. That fallback ignores the requested selection maximum, so validate the returned count against the remaining application capacity. If only one slot remains, use the single-item contract. See [Android photo picker documentation](https://developer.android.com/training/data-storage/shared/photo-picker).

### No-image input and mixed batches

1. Add an item-level checkbox labeled **No receipt image**, unchecked by default. Checking it reveals the manual fields directly on Main. Each new item defaults to image input; changing one item must not change the other items.
2. Offer an empty input card on an empty batch so the checkbox can create the first typed expense without opening the picker. **Add more** offers **Images** for multi-selection and **New item** for an additional default image card; its checkbox switches it to typed entry.
3. A typed item contains **Merchant name**, **Amount**, **Currency** (initial value `CAD`), **Date**, and **Notes (optional)**. Every source field is an optional free-text hint that helps the user describe the expense; labels suggest content without limiting what the field can contain. Use text keyboards that permit words, arithmetic, and punctuation. A date picker is an optional convenience and must not replace or restrict free-text date entry. Label the amount as the final total paid/payable, including tax/tip when applicable; helper examples must not imply a required format or required field.
4. Allow any individual source field to be blank, including merchant, amount, currency, and date. Require only some expense text across the draft, excluding the untouched CAD default by itself. The user may enter the entire expense in Merchant or Notes, such as `Walmrat, Oct 7 2026, 15+50 Canadian dollars`, leaving the other fields empty. Do not require a numeric literal, decimal syntax, three-letter currency code, ISO date, or any fixed date pattern before extraction. Accept descriptive text in all fields, including amount `15+50` or `15+50, which is 65 in total`, currency `Canadian dollars`, and date `Oct 7 2026`. Do not calculate or normalize source values locally before sending them to the LLM.
5. Typed values remain the original source draft. Only on **Extract all** or item-level **Extract / Retry extraction**, the LLM uses information from all fields together, regardless of their labels, calculates explicitly stated arithmetic, and extracts normalized fields with possible issues/suggested corrections for user review. For example, `15+50` anywhere becomes numeric `totalAmount: 65`, `Oct 7 2026` anywhere becomes `receiptDate: "2026-10-07"`, and `Canadian dollars` anywhere becomes `currency: "CAD"`. Notes are both extraction evidence and preserved user text. The LLM may suggest `Walmrat` → `Walmart` when context clearly identifies the well-known merchant; the user reviews the suggestion before acceptance. Do not convert currencies automatically. Strict expense type/format validation applies to the extracted result and export, not the source text.
6. Each typed item has **Remove**. Image items retain thumbnail/full-review removal. A batch can mix both kinds in any order.
7. Switching an item to **No receipt image** preserves its typed draft and detaches its image from the active input. An attached image can remain temporarily available for switching back before extraction. It must not be sent or exported while the checkbox is checked.
8. Switching back enables image selection and requires an image before extraction. Typed fields are not combined with image evidence in the first implementation; that would need a separate prompt/reconciliation design. Preserve draft text so the switch does not erase it.
9. Changing source type or source values after extraction invalidates that item's result revision and requires reprocessing before exporting the changed expense. Published/export-started transactions remain immutable; create a new draft to replace them.

10. Each expanded typed card shows **Extract** before its first attempt and **Retry extraction** after an attempt or when replacing existing results. This invokes the shared scheduler/provider resolution for only that item. Empty/default-only drafts and batch/provider/preparation busy states disable extraction. Keep edit-replacement confirmation, failed-retry preservation, source-revision validation and immutable saved exports. Show **Confirm and export** disabled before results exist with extraction/review guidance; use the existing transaction review action after extraction, enabled only for a current successful valid result and ready OneDrive. Keep **Retry export** and **Exported** for saved exports. No extraction action automatically exports (`REQ-A-030`, `AC-051`).

The checkbox is per item because users requested an option to include an image or not for each added item. This also supports entirely image-free batches without a second global mode that could conflict with existing image items.

### Collapsible groups and existing editors

- Use one group per input image or typed item, with stable keys. Headers show an ordinal/source label, thumbnail or typed-entry icon, processing status, transaction count, and expand/collapse control.
- Put the source review/draft, output editors, warnings, raw extraction output, and generated handoff previews inside that group. Keep existing merchant/date/amount/currency/location review and export controls; add notes where needed.
- One image producing two transactions yields one image group with two independent transaction editors and export actions. A typed item must yield exactly one transaction; reject unexpected extra transactions rather than exporting invented items.
- New items begin expanded. Preserve user-controlled expansion during completion and editing. Collapsing a group never resets fields, cancels processing, or changes export identity.
- Retrying one item replaces only its unexported results after success. Protect unsaved edits with a clear replacement confirmation, retain the old result during a failed retry, and mark its source revision so stale results cannot be exported as current.
- Removing prepared/unexported inputs is immediate, with a short Undo opportunity. Do not permit removing an item while its export is active. Removing an already exported group only dismisses its UI entry and never recalls OneDrive files or workbook rows.
- Use a `LazyColumn` and bounded thumbnail decoding for a larger batch. Preserve safe drawing/keyboard insets and accessible button targets; the thumbnail click target and (×) target must be distinct.

## State and Domain Design

Replace the singleton workflow state with stable identity and explicit input variants:

```kotlin
sealed interface ExpenseInput {
    data class Image(val preparedImageId: String, val sourceUri: String) : ExpenseInput
    data class Typed(val draft: TypedExpenseDraft) : ExpenseInput
}

data class BatchItemState(
    val itemId: String,
    val sourceRevision: Long,
    val input: ExpenseInput,
    val preparation: PreparationState,
    val extraction: ItemExtractionState,
    val reviews: List<TransactionReviewState>,
    val expanded: Boolean,
)

data class BatchRunSnapshot(
    val runId: String,
    val provider: ResolvedProviderSnapshot,
    val policy: BatchProcessingPolicy,
    val items: List<InputSnapshot>,
)
```

These are proposed types, not existing declarations. `TransactionReviewState` wraps the existing editor values with a stable transaction ID and source revision. A typed draft stores original field strings, including notes, separately from normalized results.

Use item states such as `Preparing`, `Ready`, `Queued`, `Processing`, `Succeeded`, `Failed`, and `Cancelled`, with export state per transaction. Replace index-based actions with `(itemId, transactionId)` so removing an earlier image or receiving results out of order cannot update/export another item.

All UI updates must be serialized or atomic through a reducer/`StateFlow.update`. Worker callbacks carry `(runId, itemId, sourceRevision, attemptId)` and publish only when those still match. Ignore late callbacks after remove, retry, cancellation, source edits, or a newer run. Propagate `CancellationException` rather than converting it to manual-entry failures.

Separate services for `prepareImages`, `extractPreparedImage`, `reviewTypedExpense`, and `exportConfirmedTransaction`. Reuse shared parsing and validation; keep orchestration out of composables and `MainActivity` wiring.

### Prepared image storage and lifecycle

- Stage processed bytes in private app files with item-scoped references; avoid holding every full bitmap/base64 request in UI state. Decode thumbnails lazily and load full previews only when opened. Preparation uses bounded workers, initially one, independently of inference concurrency.
- Freeze preprocessing settings at preparation time. The preview and extraction use the same staged bytes. A later setting change affects new images; replacing existing preparation requires an explicit action and result invalidation.
- Retain the batch in the activity-scoped ViewModel across Main/Settings navigation and configuration changes. Persist recoverable drafts/item references in a dedicated batch store, using Room metadata and private files rather than placing image bytes in `SavedStateHandle`.
- After process death, restore source drafts, completed editable results, and export identities; mark interrupted inference as retryable. Do not automatically resend typed data or images on restart. Restore an incomplete preparation from its retained URI grant when possible, otherwise ask for reselection.
- Persist/remove staged file references consistently and clean abandoned files only after verifying that no active batch or retryable export references them. An export owns its own immutable image snapshot before input removal can release the preparation file.
- Keep inference within the existing foreground/ViewModel lifecycle rather than introducing a background job. When the app loses foreground, stop dispatching queued items; cancel/drain active work safely. Resume requires an explicit action and preserves completed results. Opening Settings inside the app does not discard the batch.

## Batch Scheduling and Local-Model Guidance

### Recommended policy

Use one request per input item. **Extract all** starts an asynchronous queue; it does not combine all images into one model prompt. Separate requests preserve source/result mapping, isolate failures, and keep image context sizes predictable.

Enforce a hard application ceiling of **three in-flight item requests**. The delay alone must never be treated as a concurrency limit. Image and typed requests share the same provider budget, including item retries and compatibility-recovery calls.

- **On-device LiteRT-LM:** start with concurrency **1** and no arbitrary fixed delay between completed items. Keep a provider-wide gate so verification/retry cannot overlap another inference. Serialize engine access and close each conversation reliably. Reusing a loaded engine across a serial batch is a follow-up optimization that must be verified against the repository's pinned runtime; create a fresh conversation per expense to prevent context contamination.
- **LM Studio/local server:** start with concurrency **1** and a **3.5-second minimum interval between request starts**. Allow a Settings policy of 1, 2, or 3 concurrent items; raise it only after measuring the target machine with representative images. Three concurrent requests are useful when the model server has sufficient prediction slots and memory.
- **Other OpenAI-compatible endpoints:** retain the configurable 1–3 ceiling and initial 3.5-second start spacing. Hosted endpoints can use a shorter interval after provider limits are known; no hostname or model-name heuristic establishes safe concurrency.

The 3.5-second interval is a proposed conservative application default, not a provider requirement. For a concurrency-three run with long requests, dispatch A at t=0, B no earlier than t=3.5, C no earlier than t=7.0. Dispatch D only after a slot is actually released and at least 3.5 seconds since the most recent start. A single dispatcher/monotonic clock enforces both conditions.

LM Studio documents continuous batching and a configurable **Max Concurrent Predictions** setting. Match the app limit to the actual loaded model/server configuration rather than assuming the provider can execute three requests simultaneously. See [LM Studio parallel requests](https://lmstudio.ai/docs/app/advanced/parallel-requests).

Google documents potentially expensive LiteRT-LM engine initialization, background execution, and explicit engine/conversation cleanup. Serial on-device processing is an engineering recommendation based on this application's current per-request engine lifecycle and device resource constraints; it is not a claim that every LiteRT-LM API prohibits concurrent engines. See [LiteRT-LM Android lifecycle](https://developers.google.com/edge/litert-lm/android).

### Scheduler implementation

1. Validate eligible items, then resolve the effective provider once at **Extract all** activation. Snapshot profile configuration, effective opt-in, model ID, processing policy, typed drafts, and prepared-image revisions. Securely resolve credentials inside the operation scope; never persist keys in batch state.
2. Queue IDs in stable input order. Use structured coroutines, a bounded worker set/semaphore, and one rate gate. Acquire an execution slot before constructing large image requests; release it in `finally` only after the underlying operation has actually ended.
3. Execute blocking clients on the appropriate background dispatcher. Make the HTTP transport and provider adapter cancellation/deadline-aware. `withTimeout` around a blocking call alone does not guarantee cancellation; do not release a slot while abandoned native/network work still runs.
4. Publish results independently in the original group order. Supervise item failures so one invalid response does not cancel siblings. Preserve per-item raw output only under the current Debug setting.
5. Prevent repeated **Extract all** activation from creating a second queue. While a run is active, allow viewing/collapsing and editing completed transaction reviews; disable source edits, Add more, extraction retry, and export until the run finishes. Support removing queued/active items by tombstoning their IDs and cancelling/draining their jobs.
6. Add **Cancel remaining** to stop queued work and safely cancel/drain active work. Retain completed results and source drafts; item removal/cancellation must never publish a late result or begin export.
7. Preserve the client's existing one-time structured-output compatibility recovery, but route every outbound inference start through the same rate gate. An item's permit stays held across recovery; never bypass the concurrency ceiling.
8. For rate-limit responses, honor valid `Retry-After` in a provider-wide cooldown. If absent, propose bounded exponential backoff with jitter (approximately 4, 8, 16 seconds), at most two scheduling retries. Retry transient network/5xx failures only within the same bounded attempt/deadline policy; do not auto-retry authentication, invalid input, or persistent output-validation failures. Respect cancellation throughout.
9. Make timeout, attempt count, and test clock injectable. Define an initial per-item total deadline (including backoff/recovery) appropriate to existing transport limits, then tune it from real-device/server measurements. Present timeout as an item failure, retaining its draft and retry action.

Add concurrency/start-spacing controls to app Settings in the first release, with an enforced on-device concurrency of one. Keep policy outside provider-profile transfer initially, avoiding an unrelated profile schema change. Snapshot policy once per run.

Benchmark 1, 2, and 3 concurrent requests with a fixed representative image set: total batch time, median/tail item latency, memory pressure, device heat, and validation/error rate. Choose the fastest stable setting; a three-request configuration is not an unconditional local-model best practice.

## Typed-Input LLM Contract and Validation

- Add a dedicated `TypedExpenseReviewPrompt` and pipeline method using `ReceiptModelClient.extractFromReceiptText`. A provider configured for direct-image input must still send a text-only request for typed entries. Never invoke the image loader, OCR client, or image upload for an image-free item.
- Serialize all labeled original fields safely as strings, including blanks, amount, currency, date, and notes. Treat all user field content as expense data, never instructions. Tell the LLM that labels are organizational hints, not boundaries: merchant/date/amount/currency facts may appear in any field, including Notes, and the full expense may appear in one field. Extract exactly one expense from the combined evidence using canonical `receiptDate` (ISO `yyyy-MM-dd`), `merchantName` (nonblank string), `totalAmount` (finite non-negative JSON number), and `currency` (uppercase three-letter code), plus typed-review issues/suggested corrections. Keep any typed-review schema separate from the existing image `receipts` schema unless backward-compatible reuse is verified.
- Reuse existing result parsing where possible, adding a typed-review result adapter for issues/corrections rather than silently teaching image parsing to accept arbitrary response formats. OpenAI-compatible JSON-schema requests must use the matching typed schema and remain valid when `response_format` recovery is applied.
- Carry notes end to end as user text and use their content as extraction evidence for any receipt field. Do not strip extracted facts from notes, require the model to rewrite notes, or use model output as the sole source for them; preserve the original and expose any optional suggestion separately.
- Before dispatch, check only that the combined draft contains some expense text; all individual fields may be blank. An all-blank/whitespace draft, or the untouched CAD default alone, is empty and must not start inference. Preserve original strings in persistence and the request. Do not run amount/currency/date parsers, per-field required checks, or regex format checks as source eligibility gates.
- Use the CAD default only when no explicit currency is supplied anywhere in the expense text. An explicit currency in Merchant, Notes, or another field takes precedence over the default. Conflicting explicit facts across fields require an issue and user resolution; do not favor a field merely because its label matches the target property.
- In the prompt, instruct the LLM to evaluate explicitly supplied arithmetic using decimal-safe monetary semantics and parse unambiguous natural-language dates and currency names. `15+50` and `15+50, which is 65 in total` both yield 65; `Oct 7 2026` yields `2026-10-07`. Do not infer additional tax/tip or convert currencies. Contradictory totals, unclear currency, ambiguous dates such as `05/10/2026`, impossible dates, and missing facts require visible issues and user resolution rather than a guessed exportable value.
- After extraction, deterministically validate the structured result: reject missing required output, invalid/non-finite/negative amounts, malformed currency codes, impossible or non-ISO dates, and unexpected extra transactions. Use decimal-safe amount parsing rather than floating-point arithmetic. Unresolved output must block export while retaining the source draft for correction/retry or manual fallback.
- Show the original text alongside normalized results, including computed totals and parsed dates. For a recognizable well-known merchant, the LLM may propose a typo correction such as `Walmrat` → `Walmart`, with the original and suggestion visible for user acceptance. If the name could refer to several merchants or an unfamiliar business, retain the supplied name and flag uncertainty instead of inventing a brand. Surface material date/amount corrections for explicit review. Normalization and accepted suggestions must not overwrite the source draft.
- Keep original values and suggestions visible during review. Require user confirmation before export even if the model reports high confidence. Image-free records export as `manual` to reflect their typed origin; never let LLM confidence relabel them as image-verified evidence.
- If the LLM fails, retain all typed fields and explain the failure. Let the user retry or enter a structured result through the existing manual fallback after deterministic result validation and explicit confirmation. Free-text expressions cannot bypass export validation through fallback. A failed call must not clear the draft or fabricate output.

Remote opt-in applies to typed merchant/amount/date/notes just as it does to receipt images/OCR. Changing providers while a run is in progress affects the next run, not active or queued snapshots. Revoking remote opt-in should stop further remote dispatch and cancel/drain active work; retry requires a newly resolved permitted provider.

## OneDrive Handoff and Excel Compatibility

### Proposed Version 3 contract

Keep existing image exports as Version 2 for compatibility. Introduce Version 3 for image-free exports, with an explicit discriminator and null image fields. Individual confirmation keeps one JSON file per transaction. The 2026-10-07 Export All revision additionally publishes one combined JSON array of those same expense objects.

Proposed additions/constraints:

- `schemaVersion: 3`.
- Required `inputSource: "typed"` and `hasReceiptImage: false` for the first Version 3 implementation.
- Required `receiptImageRelativePath: null`. `receiptImageUri`, `originalImageFileName`, and `receiptPhotoLink` must be null/absent for these records. No empty-string or placeholder image path.
- Keep existing required expense identity, export timestamp, device ID/name, date, merchant, numeric amount, currency, and status fields. Require `extractionStatus: "manual"` for typed-origin exports.
- Include optional `notes`, preserved exactly except any intentional user edit. Version 2 can also include notes through the existing optional contract.

Version 3 initially accepts only the explicit typed/no-image combination. Existing Version 2 remains strictly image-backed. Reject inconsistent discriminators or an unsupported future Version 3 image combination rather than silently skipping its image validation. Do not downgrade typed expenses to legacy Version 1: the live processor does not accept that version.

### Android export and migration

- Give export records explicit source kind/schema version and nullable image URI/path/snapshot fields. Add notes to review, export DTO, persistence, and JSON preview.
- Migrate existing Room export rows as image-backed Version 2 with existing paths intact. Confirm the current database version before choosing the new version; preserve pending retries and exported identities. Never use destructive fallback migration.
- Image-backed exports retain JPEG-first publication followed by temporary JSON and final-name commit. Image-free exports skip folder/image operations and publish temporary JSON followed by the same final-name commit.
- Reuse one expense ID, export timestamp, JSON filename, and immutable reviewed payload across retries. Removing an input group must not delete a persisted retry record or a file owned by that export.
- Use a schema-aware JSON serializer/preview instead of calling `toVersion2Json` for every record. Typed success messages say the expense information was exported; image-backed messages retain their existing receipt-image wording.

## Confirmed Implementation Decisions

- Use an item-level checkbox and mixed batches, with one image per input group and existing multi-transaction output retained.
- Start with 20 total input items, serial on-device inference, default remote concurrency one, a configurable server ceiling of three, and 3.5-second remote start spacing. These defaults are conservative and tunable; live measurements are pending.
- Export typed-origin entries as manual Version 3 JSON with explicit no-image provenance; retain image exports as Version 2. Preserve notes in handoffs without introducing a new Excel column mapping.
- Require user resolution of ambiguous dates and confirmation of material LLM corrections. Do not silently guess absent expense facts.

The original batch decisions and free-text no-image revision are implemented and automatically verified as recorded above. Live model interpretation and production rollout are separate. Combining several photos into one expense, converting non-CAD currencies, workbook notes columns, and background inference remain outside this release.

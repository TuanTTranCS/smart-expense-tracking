## Setup and contract

Provision the model yourself, import it using the companion's local-model controls, declare image support, choose the GPU text/vision backends, and load it. Open Server, save the port/API path and optional key, then explicitly Start. Saved edits apply after Stop/Start; the active endpoint remains a separate snapshot. Keep both app keys aligned when authentication is enabled. Android may stop the process; serving is nonsticky and the foreground notification provides Stop. The service uses `specialUse` with a same-phone AI-serving subtype, following [Android's foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use).

Contract version 1 uses authenticated `POST /requests` preparation, instance/request headers on one non-streaming chat request, and DELETE/GET drain acknowledgements. Text or one inline JPEG/PNG is accepted; remote image URLs, streaming, tools, `response_format`, and per-request sampler overrides return explicit 400 errors. Sampling uses the loaded model's settings. Limits are 12 MiB request, 8 MiB decoded image, 16 megapixels, 8192 maximum dimension, and 1 MiB escaped response. Unconfirmed cleanup quarantines the process-wide coordinator; recreating a service cannot bypass it.

Identical golden fixtures are stored in this repo's `fixtures/mobile-server-contract-v1` and the companion's `Android/src/app/src/test/resources/contract-v1`. The implemented 10b client consumes this contract; paired native validation remains Pending.

### Callback cleanup and verification diagnostics revision

Native terminal handling now atomically fences duplicate completion and late chunks, then dispatches cleanup onto a dedicated daemon executor. The existing handler retains active-native ownership and server admission through conversation reset; only then can it acknowledge completion and allow the HTTP response. Existing timeout/quarantine behavior remains. The native regression models a close waiting for the callback to return and separately blocks cleanup to prove that acknowledgement remains pending; it also covers concurrent terminal events, in-flight chunks, reset failure and conversation invalidation. This removes the unsafe callback boundary without claiming device resolution.

Independent review caught cancellation before native start: a prepared handle's stop can now schedule asynchronous cleanup. `OpenAiServer` therefore awaits terminal completion whenever a prepared handle exists, even if generation never started, before disposing images/releasing admission. Matching real TCP unit and Android tests prove that DELETE remains pending, new preparation remains unavailable during quarantine, no native start occurs, and terminal cleanup permits recovery.

Source inspection confirms:

- `OpenAiServer.chat` calls `InferenceCoordinator.claim` before reading/parsing the chat body. Clients must first send `POST <base>/requests` with `{}`, then copy its `instanceId` and `requestId` into `X-Companion-Instance` and `X-Request-Id` on chat. Missing/wrong instance headers return HTTP 409 `instance_mismatch`; a valid instance with a missing/unknown/inactive request ID returns HTTP 409 `request_not_active`.
- `GET <base>/models` does not require prepared-request IDs. Successful discovery therefore does not prove that a client implements the chat contract.
- `LlmChatViewModel` invokes `model.runtimeHelper.runInference` directly. Built-in chat does not pass through the HTTP route or its parser.
- After valid preparation/headers, `ChatRequestParser` still rejects `stream: true`, assistant/history replay, `response_format`, tools and request sampling overrides. Turning streaming off alone cannot remove the preparation requirement.

The mandatory preparation/drain extension is explicit in 10a and implemented by 10b.

## Goal

1. Automatically move successfully exported expenses from the active workflow into a persistent History tab, keeping the existing ability to delete/remove them locally.
2. Supply today's full reference date to image and typed-expense LLM extraction, with guidance to infer unclear date formats from that reference.
3. Allow eligible exported expenses to be edited and explicitly re-exported. Add `itemType` to every exported expense object: `pending` for new expenses and pending updates; `processed` for updates to expenses already processed.
4. Let users verify each image-backed History expense through a tappable receipt thumbnail opening the existing full-screen zoomable viewer (option 2).

Implementation follows the Kotlin/Compose/Room/coroutine architecture in [PLAN.md](PLAN.md). ## Feature 1: Persistent History

### User behavior

- Add **Expenses** and **History** views within the receipt workflow; preserve Settings navigation. Expenses contains active drafts, extraction/review work, and failed/incomplete initial exports.
- After final publication is confirmed and the completion state is durable, the corresponding transaction disappears from Expenses and appears once in History. Never move it when only an image or temporary JSON upload has succeeded.
- For an image yielding several transactions, move each successful transaction independently. Keep its unexported siblings and their source available. Remove the active input group only when no active transactions/work remain.
- For Export All, reconcile the durable batch commit before moving members; repair interrupted per-member completion writes on restart. Do not change the committed list membership.
- Show expense date, merchant, amount/currency, source type, export time, and publication status. Show OneDrive processing status separately, with refresh time when known. Display newest exports first with stable ordering.
- History remains readable offline and after process death. Switching views preserves active drafts, scroll/selection where practical, and edit drafts.
- Keep **Delete** with the current local-removal meaning and Undo behavior. It removes the expense from the visible local History; it does not delete the OneDrive handoff, receipt image, or Excel row. Retain minimal internal identity/retry metadata needed to prevent resurrection or duplicate publication. This follows the existing removal implementation.
- Prevent deletion during publication of that expense. Only clean private files when no active draft, History preview, Undo window, or pending operation references them. History must still render text if a legacy local image is unavailable.

### Receipt thumbnails and viewer — option 2

- Add a compact thumbnail beside the merchant/date/amount on every image-backed History card. Fit the complete receipt inside the thumbnail without cropping. Make the target accessible with an expense-specific **View receipt** label and at least a 48dp touch area; preserve readable fields and existing actions at large text sizes and narrow widths.
- Tapping the thumbnail opens the existing selected-receipt viewer adapted for History: complete image fitted initially, pinch-to-zoom, bounded pan, visible Zoom in/Zoom out controls, Close and Android Back. Reset zoom on reopen or expense change. History viewing exposes no Remove action and does not enter correction editing.
- Resolve the expense's persisted `normalizedImageLocalPath` first through the private export image store. Show the normalized JPEG actually exported, rather than silently substituting the picker original or a potentially different extraction preview. Label it **Exported receipt copy**; the existing sub-200-KB export may have less detail than the original photo. Original-resolution retention is outside this follow-up.
- If the local copy is missing or undecodable, retain a tappable receipt placeholder. Download only when the user opens it or explicitly retries, using `receiptImageRelativePath` and the export's verified account/drive association. Reuse Graph authentication/transport; never fetch an old account's path from a different signed-in account. Legacy rows with unverifiable remote ownership remain locally viewable when possible and otherwise explain why recovery is unavailable.
- Store validated downloaded bytes in an app-private cache keyed by remote account/drive/image identity; generate a small thumbnail from the same image. Cache writes are atomic, image reads/decoding run off the main thread, and memory/disk caching is bounded. Load local thumbnails lazily for visible cards; opening History must not download every receipt. Do not persist temporary download URLs as receipt identity.
- Expose loading, offline/not cached, reconnect/account mismatch, permission denied, missing remote file, and invalid-image states with actionable retry where applicable. A broken preview never hides the expense text or its other available actions. Typed expenses show **No receipt image** and start no image read/download.
- Bind asynchronous results to the selected expense/image/account identity. Closing the viewer, changing expense, navigating away or switching accounts cancels or ignores stale requests. Viewing never invokes inference, uploads images, republishes JSON, changes processing status or mutates published values/correction drafts. It works independently of correction eligibility and consumer capability.
- Protect files referenced by visible History, an open viewer, active siblings, the Undo window or retryable operations. Local Delete/Undo retains its existing semantics and never deletes remote images. Cache eviction must not delete retained export images or files owned by other operations. Match each expense to its own saved image reference, including multiple transactions originating from one image and Export All members.

Implementation touchpoints: `ReceiptHistoryScreen.kt`, `ReceiptWorkflowViewModel.kt`, shared viewer components in `ReceiptWorkflowScreen.kt`, `AndroidReceiptExportImageStore.kt`, and a testable History-image resolver/cache using the existing Graph transport and authentication. Reuse persisted export references; add a Room migration only if new durable metadata is necessary, preserving all existing History/export/correction records.

### Persistence and restoration

- Query History from the export repository, not from only the current batch draft. Expose observable completed records and reconcile committed batches before projecting results.
- Plan an additive migration from export database v4 to v5 for History visibility, completion metadata, remote identity/status metadata, and persisted edit-operation state. Keep batch-draft and model-profile database versions independent unless their actual schemas need changes.
- Preserve existing IDs, timestamps, payloads, paths, status, and batch membership. Existing completed export rows become visible History entries. Existing failed/in-progress exports remain recoverable and retain their original retry payload.
- Legacy rows have no reliable historical completion time: use their saved creation time as an explicitly defined ordering fallback, without claiming it is the upload completion time.
- Do not claim that expenses removed before this feature were intentionally hidden from History: there is no existing deletion marker in the export database. Existing completed rows are the recoverable baseline.
- A saved local visibility marker must survive refresh, navigation, app restart, and batch reconciliation.

## Feature 2: Current-date extraction context

### Prompt contract

Generate prompts at extraction time using an injectable clock/date provider and the Android device's local timezone. Format the date with an explicit English locale and `MMM d, uuuu`, for example:

```text
Current reference date: Oct 16, 2026.
If a date in the expense text or receipt image is unclear or uses an ambiguous
numeric format or two-digit year, use this reference date and the surrounding
expense evidence to infer the most plausible intended date. For example,
10/15/26 with this reference date means October 15, 2026 (2026-10-15).
Preserve clearly stated dates, including older dates. Do not substitute today's
date for a missing date or turn an impossible date into a valid one.
```

- Apply the context to direct-image extraction, OCR-text fallback, and the dedicated typed-expense prompt, including all three provider categories and API output modes.
- Capture one reference date per extraction attempt and reuse it for its image/OCR fallback and protocol/schema recovery calls. A later user-triggered retry captures the then-current device-local date. Do not cache today's date in a singleton prompt value.
- Retain original typed strings and image evidence. Let the LLM infer the date; do not introduce a local numeric-date parser for free-text input.
- Revise the typed prompt's blanket prohibition on date guesses. Reference-based guesses may be proposed for review; conflicting evidence or dates with no plausible interpretation still require correction. Keep uncertainty visible through the existing confidence/issues/review mechanism without making every allowed inference automatically unexportable after confirmation.
- Preserve strict real-calendar/ISO result validation, explicit user confirmation, missing-fact handling, and invalid-output export blocking. A current date is context, not evidence that every expense occurred today.

### Code touchpoints

- Shared: `ReceiptExtractionPrompt.kt`, `TypedExpenseReviewPrompt.kt`, `ReceiptExtractionPipeline.kt`, `ReceiptModelClient.kt`, `OpenAiCompatibleReceiptModelClient.kt`, and `AndroidLiteRtLmReceiptModelClient.kt` under `src/main/kotlin/com/hugo/smartexpense/extraction/`.
- Android app: provider wiring; confirm that supplied prompts propagate unchanged. The same-phone companion should not need inference-protocol changes merely to receive dated prompt text.
- Pass an immutable extraction context through the shared path so ordinary and recovery requests cannot independently read different dates at midnight.

## Feature 3: Edit and re-export exported expenses

### Remote status is distinct from local export status

Use explicit states such as Checking, Pending, Processed, Needs review, Error, Missing, and Unavailable. A failed request, stale cache, missing queue file, or archived batch list is not proof of successful processing.

- Resolve the expected file under the connected drive/account and validate its expense ID and source contract. Retain drive/item identity, parent, eTag, and observed payload/version information where available; prevent a different signed-in account from receiving an old account's correction accidentally.
- For individual exports, check the pending singleton and its known done/review/error locations.
- For Export All, first resolve whether the original list still owns the pending member. After expansion, locate the deterministic singleton in the queue or outcome folder. `receipt_batches_expanded` establishes expansion only, not the outcome of every member.
- A list and singleton that coexist during partial expansion require reconciliation; do not overwrite one while treating the other as nonexistent. Missing/contradictory evidence disables re-export and offers Refresh while preserving the edit draft.
- Check eligibility when opening Edit and again before publication. Cached status may support display, but cannot authorize a remote replacement.

### Editor and publication

- Both pending and processed History records expose **Edit** when their remote identity/status can be established. Reuse structured review fields for merchant, date, amount, currency, location where supported, and typed notes. Keep identity, source type, image path, and transport fields out of the editor.
- Edit creates a separate persisted draft. **Cancel** restores the published view. **Re-export** validates and explicitly confirms the corrected fields. Saving a local draft does not publish or invoke the LLM.
- Mark edited handoffs `extractionStatus: "manual"`. Preserve the stable expense ID, original creation timestamp, source provenance, existing normalized image reference, and unchanged fields/notes. Avoid a new expense ID that would cause another Excel insertion.
- Keep the last successfully published snapshot immutable. Each confirmed correction creates its own immutable operation snapshot; retries reuse that operation and its exact payload. New changes become a later operation, not mutation of an in-flight retry.
- A failed correction stays in History with the original published values, retained edits, and actionable Retry re-export. Only acknowledged publication updates the displayed published snapshot.
- Serialize conflicting operations per expense and per shared batch file. Prevent duplicate taps, stale completions, simultaneous original retry/correction, and History deletion during publication.
- For a still-pending list member, preserve every other member, their order, identities, and payloads. For an expanded member, target its singleton; never replay the original entire list to correct one expense. Retain unknown compatible JSON fields during round trips.
- Reuse the existing normalized image for field-only corrections; do not re-extract or upload another image unnecessarily. Verify the referenced image still exists before publishing a processable image-backed handoff.

### `itemType` contract

- Every newly generated singleton object and every Export All member includes exactly `"itemType": "pending"`.
- Re-export of an expense confirmed still pending uses `"itemType": "pending"`.
- Re-export of a done expense uses `"itemType": "processed"` and requests correction of its existing Excel entry, retaining the original expense ID.
- This discriminator is separate from `schemaVersion`, image/typed `sourceType`, extraction confidence/provenance, local publication status, and the observed OneDrive folder. An original JSON with `pending` can already be in the done folder; the field does not refresh itself when Windows moves the file.
- Retain image Version 2 and typed Version 3 semantics. Treat the field as an additive extension only if compatibility checks prove this safe. New writers always emit it; readers accept missing `itemType` as legacy new-item semantics and reject unsupported values. Never silently process a `processed` correction as a new insert.
- Update Kotlin serialization, Debug previews, [handoff-contract.md](handoff-contract.md), fixtures, and PowerShell validation together. Add any correction revision/operation identifier needed by the chosen protocol explicitly to the contract before implementation; `itemType` alone cannot order retries or distinguish two corrections.

### Concurrency and downstream correctness

Checking the folder and replacing a file are separate operations. Windows can read/process the old version while a correction is being uploaded, and OneDrive local sync can lag Graph. An eTag does not lock a Windows process's already-read bytes.

- Before shipping re-export, prove a coordinated publication/consumer protocol with a revision or payload fingerprint, stable operation identity, and detectable stale reads. Do not rely solely on a path existence check followed by the existing unconditional temporary-file rename.
- Use Graph conditional operations where documented and verified; a changed eTag, HTTP 409/412, moved parent, or missing file requires refresh/reconciliation. Do not recreate an apparently missing pending file or overwrite an archived file blindly.
- Microsoft documents `if-match`/HTTP 412 for [metadata updates](https://learn.microsoft.com/en-us/graph/api/driveitem-update?view=graph-rest-1.0) and [upload-session creation](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0). Verify the selected content-commit mechanism for personal OneDrive, including changes between session creation and commit; metadata preconditions alone do not establish an atomic cross-process update.
- The implementation design spike must settle the exact file/revision naming, acknowledgement, retry, and archival protocol. Preserve existing image timestamp/path correlation. Use disposable queue folders to exercise consumer reads concurrent with cloud publication and delayed sync.
- If a pending correction loses the race to processing, retain it and surface that processing changed. Never report it as applied merely because upload succeeded. Reconcile it through the processed-update policy with the correct discriminator and preserved operation identity; require explicit confirmation if reconciliation changes the correction the user approved.
- Replace expense-ID-only skipping with revision-aware handling. Resolve the original row from durable identity/state and verify its old fingerprint before changing F/G/H; do not overwrite a row changed independently in Excel. Handle date changes across monthly sheets with a journal/recovery strategy, duplicate conflicts, and preservation of all unrelated cells/formulas. Retries must produce one final corrected entry, including crashes after workbook save but before state/archive updates.
- Publish processed corrections into the consumer's watched queue using the agreed revision-aware naming/identity contract; editing only the archived JSON will not trigger the processor. Preserve the prior archived version and correlate the correction with its original expense. Show JSON publication and confirmed Excel application as distinct states.
- Deploy compatible consumer behavior before enabling re-export in the app. Do not modify the production workbook, scheduled job, or live queue as part of planning or disposable verification.

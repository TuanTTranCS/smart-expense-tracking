## Goal and Scope

Add **Duplicate profile** to the saved remote-profile cards on Settings. Copy all provider settings and the stored credential into an independent profile whose display name is the source name followed by exactly ` (copy)`.

Add **Load models** and a searchable model picker to the remote-profile editor. Fetch model IDs from the configured provider instead of requiring users to look up and type every ID. Keep manual Model ID entry available.

Follow the Kotlin, Compose, Room, coroutines, provider abstractions, and immutable extraction snapshots in [PLAN.md](PLAN.md). Profile management belongs on Settings; Main continues to use saved provider configurations.

Confirmed implementation scope on 2026-10-04: the existing OpenAI-compatible profile contract, including LM Studio and OpenRouter. Hugo approved compatible discovery with native API adapters deferred. Native provider APIs remain an optional extension described below.

- `android-app/.../modelprofile/ui/ModelProfilesPanel.kt` owns saved-profile cards and the editor. `ModelProfilesViewModel.kt` owns mutations, drafts, validation, and provider tests.

- `android-app/.../connectivity/ModelsEndpointChecker.kt` already performs cancellable GET requests, accepts an optional key and relative path, parses `data[].id`, returns empty lists successfully, rejects redirects, limits responses to 1 MiB, and redacts failures.

## Feature A: Duplicate Profile

### User behavior

1. Each saved remote-profile card exposes **Duplicate profile**, with an accessible label identifying its source. Put it on a separate row or use wrapping actions so Select/Edit/Delete/Duplicate fit narrow screens.
2. Duplicate the saved profile identified by that card, whether or not it is selected for extraction. The built-in on-device provider is not a saved remote profile and has no duplicate action.
3. Save the copy immediately and show `Duplicated <source name> as <copy name>.` The normal Edit action lets the user change it afterward.
4. Copy `baseUrl`, `modelId`, `inputMode`, `structuredOutputFormat`, and `showTailscaleToggle`, plus the stored credential if present. Preserve the source unchanged.
5. Generate a fresh profile ID, a fresh `ModelProfile.credentialAlias(newId)`, and fresh creation/update timestamps. These identity fields cannot be shared with the source.
6. Use exactly `<source displayName> (copy)`. Repeating duplication of the same source may create equal display names with different IDs. Duplicating an existing copy appends another ` (copy)`; do not silently introduce numeric suffixes.
7. Keep the current selection and remote-provider opt-in unchanged. A copied Tailscale flag does not issue a connect/disconnect command. Duplication works offline and while remote providers are disabled.
8. Duplicate is offered from the saved list, which is hidden during editing. Unsaved metadata and API-key text are never treated as the source.

### Service and persistence

Introduce a testable `DuplicateModelProfileService` in the Android model-profile domain layer, depending on `ModelProfileRepository`, `WritableApiKeyStore`, an ID factory, and a clock. Keep credential values inside this service/store boundary; do not place them in duplicate results, messages, logs, Room, or persistent UI state.

Recommended operation:

1. Acquire the profile-mutation guard before launching asynchronous work. Ignore repeated activation while busy; serialize duplication against edit/save/delete/import/credential-clear operations.
2. Resolve the source again by ID, rather than trusting a stale card object. If missing, return an actionable failure with no mutation.
3. Create the copy from the saved source snapshot using `copy(...)`, replacing only name, identity, alias, and timestamps. Copy future persistent provider fields too; add tests when new fields are introduced.
4. Read the source credential through its actual alias. No credential is a valid state; a secure-store read failure is a failed operation, not permission to silently omit the key.
5. If a credential exists, write it durably under the new alias before publishing the Room row. Add a checked durable-write operation to the credential-store contract/Android implementation for this flow, performed on an I/O dispatcher; `apply()` alone cannot confirm durability. Never reuse the source alias.
6. Insert the copy with conflict-abort semantics, not an upsert that could overwrite an existing profile. Add a repository/DAO insertion operation as needed. Use a Room transaction to verify that the source still matches the snapshot and insert the new row; if changed/deleted, fail and let the user retry.
7. If credential writing, insertion, or cancellation before insertion fails, remove any newly written alias. Run compensation despite coroutine cancellation and return sanitized errors. Cleanup failure must also be reported safely. Never remove the source key.
8. Treat a committed Room insert as success even if the screen stops observing immediately afterward; do not delete its key during cancellation cleanup. If cancellation makes the insertion result uncertain, query the new ID in a non-cancellable cleanup context before removing its alias. Publish success only after durable credential storage and successful insertion.

Room and encrypted preferences cannot share one transaction. Key-first ordering prevents a committed copy from being published before its credential is durable. A process death between stores can leave an unreferenced encrypted alias; document this recovery limit rather than promise cross-store atomicity. Do not add broad credential cleanup without a reliable reference check.

Editing, clearing credentials, or deleting either profile must affect only its own alias. Profile exports remain metadata-only; local duplication is intentionally allowed to copy credentials, while existing import conflict-copy behavior continues to import no credentials.

## Feature B: Provider Model Selector

### Editor behavior

1. Keep the existing **Model ID** textbox. Add **Load models** beside/below it and show the configured endpoint being contacted. The request sends no receipt image, OCR text, prompt, or inference request.
2. Allow loading for both a new draft and an existing profile. Validate only discovery inputs: HTTP(S) base URL and safe credential/header values. Discovery must not require a display name or an already populated model ID; keep full-profile validation for Test/Save.
3. Snapshot the draft base URL and credential at activation. Use a nonblank unsaved API-key entry when supplied; otherwise use the saved profile's actual secure alias. A new profile with no key sends no Authorization header. A saved profile whose credential was cleared also sends no key.
4. Loading is an explicit configuration request, like the editor's existing Test action. It does not enable remote receipt extraction, select a provider, save the key, or change the remote opt-in setting.
5. Display loading, loaded, empty, failed, and cancelled states separately from inference Test status and Main's connectivity status. An empty successful response means reachable with no models to choose, not an endpoint outage.
6. Show a scrollable, searchable picker keyed by exact model ID. In the initial version, display IDs as labels. Normalize duplicate IDs and sort deterministically without changing ID spelling, case, namespace, or version suffix.
7. Picking an item changes only `draft.modelId` and invalidates any prior inference-test result. Save/Save and select remain explicit. Do not automatically choose the first returned model.
8. A manually entered/current model absent from the list remains intact and can still be saved. Errors, an empty list, or picker dismissal never clear it or prevent manual entry.
9. Cancel the request and clear endpoint-specific results when the editor closes, Settings leaves the foreground, the edited profile changes, or the base URL/effective credential changes. Retain unsaved draft edits across lifecycle cancellation. Cancel before Save/Delete/Clear credential or conflicting provider mutations.
10. Compare a request token/editor generation before publishing a result, including for test doubles that ignore cancellation. Ignore stale responses. Track credential changes with an in-memory generation counter; never use an API key as a cache key, loggable token, or persisted fingerprint.

### Compatible endpoint implementation

Add an injectable `ProviderModelCatalogService` with typed success/failure results and a normalized `AvailableProviderModel(id, label)` value. The initial implementation wraps `ModelsEndpointChecker`; a successful `Reachable(modelIds)` becomes deduplicated, sorted picker items. Keep catalog state transient in the ViewModel and scoped to the editor request. No database or provider-transfer schema change is needed for this initial scope.

Use the existing base URL as the API prefix and append relative `models` once:

- LM Studio: `http://host:1234/v1` → `http://host:1234/v1/models`.
- OpenRouter: `https://openrouter.ai/api/v1` → `https://openrouter.ai/api/v1/models`.
- A custom compatible gateway uses its configured prefix in the same way; do not guess the root URL or add another `/v1`.

The checker already validates the stricter network inputs. Reuse those rules, bounded I/O, redirect rejection, and connection cancellation. Bound the whole catalog request to 10 seconds, with the existing positive connect/read timeouts; do not start automatic discovery polling or inference-based fallback calls.

Give safe recovery messages for denied access, not found/unsupported listing, rate limiting, server failure, timeout, invalid JSON/schema, oversize response, and network unavailability. Never expose response bodies or credential-bearing URLs. For a response exceeding the current 1 MiB limit, retain manual entry and explain the listing could not be loaded; do not silently remove the cap. Measure representative catalog sizes before considering a separately tested catalog-specific limit.

## Handling Different Provider Response Formats

Parse according to the provider API contract, then normalize to one app model. Avoid scanning arbitrary JSON recursively for keys named `id`, `name`, or `model`.

### Initial format: compatible `data[].id`

The existing parser requires a top-level `data` array whose entries have nonblank string IDs. It ignores unrelated fields. That already accommodates providers adding different metadata around the same required shape. Keep missing/wrongly typed IDs as an invalid-list failure instead of coercing values or silently treating malformed data as an empty list.

LM Studio documents `GET /v1/models`; OpenRouter's `GET /api/v1/models` documents `data[].id` with additional fields such as `name` and `architecture.input_modalities`. These endpoints support the recommended compatible discovery path. See [LM Studio compatible models](https://lmstudio.ai/docs/developer/openai-compat/models) and [OpenRouter models](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties).

Listing a model does not establish receipt-image support, structured-output compatibility, account access for inference, or successful loading. The initial picker makes no capability claims based on model-name heuristics. Keep input mode/output format editable and retain the existing inference Test/Verify behavior.

### Optional adapters and richer metadata

If native APIs or capability-aware labels are included later, introduce explicit adapters responsible for endpoint path, authentication, response parsing, pagination, and ID mapping. Each adapter returns the normalized app model plus optional capability metadata with an explicit unknown state. Select adapters through provider type/configuration; do not silently switch API families after a parse failure.

- **OpenRouter metadata:** extend compatible parsing to preserve optional display name, input modalities, and supported parameters. The exact `id` remains the extraction model ID. Known incompatible capabilities may be explained, but missing metadata must remain unknown. [Official model schema](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties).
- **LM Studio native v1:** `GET /api/v1/models` uses `models[]`, `key`, and `display_name`, rather than the compatible list's `data[].id`. A native discovery adapter must verify how the returned key maps to the configured inference API; retain `/v1/models` for the initial compatible release. [Official native list contract](https://lmstudio.ai/docs/developer/rest/list).
- **Ollama native:** `GET /api/tags` returns `models[]` with model names. A native adapter must preserve exact tags and coordinate its inference path; using the provider's compatible surface is a separate choice. [Official list contract](https://docs.ollama.com/api/tags).
- **Anthropic native:** the Models API uses `GET /v1/models`, but native authentication, required version headers, and cursor pagination are provider-specific despite its `data` envelope. [Official models contract](https://platform.claude.com/docs/en/api/models/list) and [authentication overview](https://platform.claude.com/docs/en/api/overview).
- **Gemini native:** model listing uses `models[]`, resource `name`, and `nextPageToken`; an adapter must explicitly map resource names to its inference contract and handle supported generation methods. [Official models API](https://ai.google.dev/api/models).

Native discovery alone does not add native extraction support: the app currently sends OpenAI-compatible inference requests. Adding Anthropic/Gemini/native inference requires its own provider client, credentials/headers, request and receipt-output adapters, and tests. Before persisting provider type or discovery path, define a Room migration and a new provider-configuration document version accepting existing v1/v2 imports with compatible defaults. Duplicate any newly added provider fields too.

For paginated APIs, adapters must enforce an overall deadline, total byte/item/page bounds, repeated-token protection, and same-provider URL construction. Present a partial/truncated catalog explicitly; never describe one page as the complete catalog.

Official provider documentation was checked on 2026-10-04. These mappings describe implementation contracts, not runtime probing of Hugo's configured endpoints.

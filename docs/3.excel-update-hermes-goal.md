# Hermes Excel Update Goal

Last updated: 2026-09-14

## Objective

Implement and verify the Windows-side receipt processor for Smart Expense Tracking. Hermes must orchestrate a deterministic PowerShell action that reads completed Android handoff files from the locally synced OneDrive folder, updates `Canada plan.xlsx` through Excel COM, archives or quarantines each handoff predictably, and reports actionable results through Discord.

Normal processing must not require an LLM. Financial writes, duplicate decisions, file routing, and workbook updates must be decided by tested code. An LLM may help a user understand a quarantined item, but it must never approve or perform an ambiguous workbook write automatically.

Do not enable the live five-minute job as part of this goal. Finish with a paused Hermes canary after all tests and a disposable-workbook run pass. Live activation requires separate user approval.

## System Background

The Android app lets the user capture or select a receipt, extracts the receipt date, merchant, amount, and currency, and requires user confirmation before export. It uploads a normalized JPEG below 200 KB to OneDrive first. Only after the image upload succeeds does it publish the final Version 2 JSON handoff. The final `.json` file is therefore the commit marker for the image/JSON pair.

The Windows computer syncs these OneDrive-root-relative locations:

```text
Documents\2_Others\Expenses_finance\logs
Documents\2_Others\Expenses_finance\receipt_images\YYYY-MM
Documents\2_Others\Expenses_finance\Canada plan.xlsx
```

The Android contract, field names, filename rules, and image-path validation rules are defined in `docs/handoff-contract.md` and `docs/requirements.md`. Use those documents as the source of truth. Do not change the Android schema in this workstream.

## Confirmed Workbook Contract

The real workbook was inspected on 2026-09-14. Monthly worksheets use names in `YYYY-MM` format.

For monthly expense rows:

- Rows 1-11 contain income, recurring expenses, headings, and other fixed workbook content.
- Receipt transactions start at row 12.
- Column E is an existing shared-cost field and is outside this task's mapping.
- Column F contains the numeric expense amount.
- Column G contains the merchant description followed by an English month/day label, such as `T&T Mart Sep 06`.
- Column H is currently unused and will contain a relative hyperlink to the normalized OneDrive receipt image.
- Column O contains existing row formulas and must be preserved.
- The supported transaction search range is rows 12-100.

The processor must fill the first row from 12 through 100 where both F and G are empty. It must not insert a row after row 12, reorder existing expenses, or overwrite a partially populated row. A row where only F or only G is populated is occupied and must be reported as a structural warning while the search continues. If no safe row exists, leave the handoff in the inbox and report a workbook-capacity failure.

## PowerShell Interface

The entry point must support these parameters:

| Parameter | Required behavior |
| --- | --- |
| `OneDriveRoot` | Optional explicit OneDrive root. When omitted, resolve `OneDriveConsumer`, then `OneDrive`, then a validated Windows registry fallback. Fail clearly on no valid root or conflicting valid roots. |
| `InboxRelativePath` | Default `Documents\2_Others\Expenses_finance\logs`. |
| `WorkbookRelativePath` | Default `Documents\2_Others\Expenses_finance\Canada plan.xlsx`. |
| `StatePath` | Default `%LOCALAPPDATA%\SmartExpenseTracking\Hermes\processed-expenses.json`. |
| `LogPath` | Default `%LOCALAPPDATA%\SmartExpenseTracking\Hermes\processor.jsonl`. |
| `DryRun` | Perform discovery, validation, mapping, and duplicate analysis without changing the workbook, state, or handoff files. |
| `OutputFormat` | Support `Json` for tests/integration and `Hermes` for the scheduled job. |

Use exit code `0` for handled runs, including no work, successful processing, exact duplicates, quarantined input, and deferred workbook-lock outcomes. Use a non-zero exit code only for a run-level failure that prevented reliable classification or persistence. Never use a non-zero exit alone as the diagnostic; emit a structured result and write the local JSON Lines log.

The structured run result must contain `schemaVersion`, `startedAt`, `completedAt`, `outcome`, `counts`, and `items`. `counts` must include discovered, inserted, exact duplicate, review, invalid/error, deferred, and failed records. Each item must contain only `fileName`, `expenseId` when validated, `outcome`, `reasonCode`, `message`, and optional `sheet` and `row`. Do not log raw receipt contents, addresses, model output, or other unnecessary sensitive fields.

For `Hermes` output:

- Emit exactly `[SILENT]` when no final handoff files were discovered and no run-level problem occurred.
- Otherwise emit a short deterministic status suitable for direct Discord delivery.
- Include filenames and concise reasons only for review, error, deferred, or failed outcomes.

## Processing Rules

### Discovery and validation

1. Acquire a process-level lock so overlapping cron ticks cannot run the processor concurrently.
2. Inspect only files directly inside the inbox. Do not recurse into archive, review, or error folders.
3. Select only filenames matching `^expense_\d{8}_\d{6}_[0-9a-f]{8}\.json$` and process them in ordinal filename order.
4. Ignore temporary extensions such as `.uploading`.
5. Parse and validate the Version 2 handoff contract before opening Excel.
6. Validate the UUID, timestamp, `yyyy-MM-dd` receipt date, non-negative numeric amount, `confirmed` or `manual` extraction status, filename short ID, deterministic `receiptImageRelativePath`, and existence of the referenced local JPEG.
7. Accept only `CAD`. Route every otherwise valid non-CAD handoff to review without changing the workbook.
8. Treat unsupported versions, invalid JSON, missing required data, invalid paths, path traversal, missing images, and disallowed extraction statuses as errors.

Resolve the receipt image by combining the validated OneDrive root with `receiptImageRelativePath`. Reject rooted paths, `..` traversal, paths outside the OneDrive root, and paths that do not match the deterministic handoff naming contract.

### State and file routing

Maintain an atomic local state document with `schemaVersion: 1` and a `records` object keyed by full `expenseId`. Each record must contain `outcome` (`inserted` or `exact_duplicate`), `processedAt`, `sourceFileName`, and optional `sheet` and `row`. Write state through a same-directory temporary file and atomic replacement.

Use these non-recursive subfolders under the inbox:

```text
receipt_jsons_done
receipt_jsons_review
receipt_jsons_error
```

Routing rules:

- Already completed expense ID: do not open or modify the workbook; move the handoff to `receipt_jsons_done` and report it as already processed.
- Successful workbook insert: record state, then move the handoff to `receipt_jsons_done`.
- Exact workbook duplicate: record the duplicate outcome, then move the handoff to `receipt_jsons_done` without adding a row.
- Similar/ambiguous record or non-CAD currency: move the handoff to `receipt_jsons_review` and write `<handoff-stem>.result.json` beside it.
- Invalid handoff or missing/invalid image: move the handoff to `receipt_jsons_error` and write `<handoff-stem>.result.json` beside it.
- Workbook locked, read-only, structurally unexpected, full, or unavailable: leave valid handoffs in the inbox for retry and report them as deferred or failed. Do not mark them processed.

Each sidecar must contain `schemaVersion: 1`, `originalFileName`, `outcome`, `processedAt`, `reasonCode`, `message`, and a `candidates` array of `{ sheet, row }` objects when applicable. It must not copy the receipt payload. Archive moves must never overwrite an existing different file. When a destination file already exists, compare SHA-256 hashes: remove the inbox copy only when the destination is identical and state already proves completion; otherwise leave the source in place and report an archive conflict.

If state recording succeeds but moving the handoff fails, the next run must use state to avoid a duplicate write and retry only the archive move. If Excel saves but state recording fails, the next run must use the workbook-level exact duplicate check to prevent another row.

### Merchant and duplicate normalization

Build column G from the user-confirmed Android values:

1. Trim the merchant name and collapse repeated whitespace.
2. Replace the standalone word `Supermarket`, case-insensitively, with `Mart`.
3. Append the receipt date formatted with invariant English culture as `MMM dd`.

Example:

```text
Example Supermarket + 2026-09-05 -> Example Mart Sep 05
```

For comparisons, normalize merchant text by applying the same wording rule, Unicode normalization, invariant lowercase, collapsed whitespace, and conservative punctuation normalization. Compare amounts as decimal currency values rounded to two fractional digits.

Classify records in this order:

1. A completed `expenseId` is an idempotent replay.
2. The same receipt date, two-decimal amount, and normalized merchant is an exact workbook duplicate; skip and archive it.
3. The same receipt date and amount with a different merchant is a similar/ambiguous record; quarantine it for review.
4. Otherwise the record is eligible for insertion.

Parse legacy workbook descriptions only when they end in an unambiguous English `MMM d` or `MMM dd` suffix whose month matches the worksheet. Do not guess dates from free text, multiple-date descriptions, or rows without a date suffix. Do not introduce fuzzy or LLM-based merchant matching.

## Excel COM Update

Use desktop Excel COM because the workbook contains formulas, formatting, and summary logic that must remain native. Do not use Open XML, ImportExcel, Python workbook writers, or Microsoft Graph workbook APIs for the production write.

Before mutation:

1. Confirm that the target file exists.
2. Check for an existing Excel owner/lock and attempt a safe open.
3. If Excel opens the workbook read-only, close it without saving and defer all otherwise valid workbook-dependent records.
4. Validate the expected monthly-sheet headers, F/G transaction area, and `Food Expense Summary` structure.

Open the workbook once per batch. Stage every accepted change, including duplicate checks against earlier staged rows, save once after the complete batch succeeds, and close Excel in `finally` cleanup. If any workbook operation fails before save, close without saving and leave all valid, uncommitted handoffs in the inbox.

For each inserted receipt:

- Write `totalAmount` as a number to F.
- Write the formatted merchant/date text to G.
- Add a clickable hyperlink in H whose target is relative to the workbook directory, for example `receipt_images\2026-09\...jpg`.
- Preserve the row's existing formatting, formulas, E value, O formula, and unrelated cells.
- If the selected row is within 12-100 but lacks the established transaction formatting or O-row formula, extend the immediately preceding transaction-row format and row-relative formula pattern without copying its F:H transaction values or E value. Abort if the pattern cannot be reproduced safely.

### Missing monthly sheet

If the target `YYYY-MM` sheet is absent:

1. Find the latest valid monthly sheet earlier than the target month. If none exists, defer for review.
2. Copy that entire sheet through Excel COM and rename the copy to the target month.
3. Keep rows 1-11 and every non-transaction cell, formula, style, object, column width, row height, and pane setting.
4. Clear only F:H in rows 12-100. Preserve columns E and O and all other workbook structure.
5. Position the new sheet chronologically with the monthly sheets and before later non-month summary/internal tabs.
6. Validate the copied sheet before adding a receipt.

### Food Expense Summary

The summary currently uses one 89-row detail block per included month, covering monthly source rows 12-100. The processor must integrate a target month later than the summary's latest month when that month is not already represented.

To extend it safely:

1. Confirm the existing summary headers, chronological month list, `Accumulated` row, coverage-check cells, and final 89-row detail block match the known pattern.
2. Append a copied 89-row detail block for the new month and replace the prior sheet reference and displayed month with the target `YYYY-MM` value.
3. Add a copied monthly summary row immediately above `Accumulated` and set its month value.
4. Extend every summary aggregation range, accumulated total, non-empty detail count, and expected-source-row formula to the new detail endpoint.
5. Update the summary title's ending month.
6. Recalculate and require the coverage status to remain `OK` before saving.

Do not silently add a month earlier than the summary's first month, insert an out-of-order month, bridge a chronological gap, or attempt to repair an unfamiliar summary layout. Treat those cases as structural failures and leave the handoff in the inbox.

1. Run `DryRun` against a disposable workbook and fixture inbox.

5. Manually run the paused job against disposable paths and verify the Discord result.
6. Leave the job paused and the live workbook untouched.

This goal is complete only when all tests pass, the copied-workbook canary is verified, the paused cron job exists, and the relevant requirements, `README.md` if needed, `docs/PLAN.md`, `docs/current status.md`, and `docs/gap-closing-plan-details.md` accurately record the result.
